# M-issue-files — every item one file of `issues/`, ready to be one GitHub issue

**Opened 2026-10-04 by author instruction**, at row 83 of the chain and ahead of
every scheduled row (`docs/roadmap/scheduling.md`). The decision and how every
value was derived are
`issues/2026-10/04/2026-10-04-2308-every-item-becomes-an-issue-file.md`; the rules
are `.claude/rules/records.md` § The issues, their one home.

**What it delivers.** Every item the project tracks, open or closed, as one file
of `issues/` in the folder of its name's day, a card on each saying what GitHub
needs (kind, area, milestone, birth, the commit that settled it, the address of
the issue it becomes), its sequence kept by its name, and nothing ever moving
when it closes. The instrument that holds the files to that shape is
`tests/harness/cards.hero` and the record checks rewritten onto them.

**What it deliberately does not deliver**, each an issue of this milestone:
the verb that renders a file as an issue is a change to the tool's surface and
so a sitting's question (CLAUDE.md § 4); the labels and milestones on GitHub,
and the transcription itself, are outward acts, the author's every time
(CLAUDE.md § Hard stops).

**What closes it**: the three issues below it settled or carried with their
reason, the full net green on the trunk, and the tag placed over a list clean of
`blocking` and `systemic` defects, which today it is not (CLAUDE.md
§ Verification), so the tag waits for the batches that close them.

# report

## verdict

Refused, on lines 11 and 12.

- Line 11, `app(f: ident, x: 20)`: `ident` is a generic function used as a value, and it is handed to `app`'s parameter `f: (function(A) -> A)`, which is a generic parameter of the generic function `app`.
- Line 12, `ns.map(ident)`: the same thing. `ident` is handed to `map`'s parameter `f: (function(A) -> B)`, which is a generic parameter of the generic built-in `map`.

The spec lists three sources a generic function value may take its types from: a non-generic parameter, a record field, or a declared return. Neither call supplies one of these, and the spec says outright that handing such a value to a generic parameter is an error.

Smallest fix: make `ident` non-generic, at the one type the program uses it at. Line 3 becomes `function ident(x: i64) -> i64`. After that, `ident` is an ordinary function value. `app` takes `A = i64` from it, and `map` takes `A` and `B` from its signature, just as `xs.map(double)` does in the spec. Lines 11 and 12 then stay as they are. The program still means what it evidently means: apply a function to a value, with the identity as that function. The fixed program prints:

```
20
3
```

## choice_points

- **What "handed to a generic parameter" covers.** I read it as covering any parameter whose type mentions a type parameter of the callee, so `app`'s `f` and `map`'s `f` both count. Under the other reading, where only a parameter whose type is a bare type parameter counts, line 11 might be accepted with `A` taken from `x: 20`. Line 12 would then turn on the same question for `map`. I think the spec's wording ("takes its types only from a non-generic parameter") rules that reading out.
- **Which fix.** I made `ident` non-generic on `i64`, which changes one line. Another option is to keep `ident` generic and annotate a binding, `g: (function(i64) -> i64) = ident`. A binding annotation is not one of the three listed sources, though, so that might still be refused. A third option is a non-generic wrapper `function ident64(x: i64) -> i64` that calls `ident(x)`, used in both calls. That works too, but it is a larger change. The output is the same under every fix that is accepted.
- **Type of `len()`.** The spec never gives `len`'s result type. I take it to be an integer, so `.to_str()` gives `"3"`. Any numeric type prints the same.
- **Generic `ident` left unused.** Not applicable: the fix removes the generic, so the question of whether an unused top-level function is an error does not come up.

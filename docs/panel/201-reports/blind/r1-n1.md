# verdict

Refused, on lines 11 and 12.

Both lines pass the generic function `ident` as a value to a parameter of a generic function (`f` of `app` on line 11, `f` of `map` on line 12). `ident` is not called there, so its type parameter `A` cannot be taken "from the arguments". The only other source is "the type the context asks for", and the specification says a generic function's parameter asks for none. Nothing fixes `ident`'s `A`, so the checker refuses both uses. On line 12 the error also spreads: `map`'s `B` can only come from `f`'s type, and that type is not determined.

The smallest fix is to give `ident` a concrete type once, through an annotated binding (an annotated declaration is a context that asks for a type), and pass that binding instead. With that fix the program prints:

```
20
3
```

# program

```
# Apply a function to a value, and the identity.

function ident<A>(x: A) -> A
    return x

function app<A>(f: (function(A) -> A), x: A) -> A
    return f(x)

function main()
    ns = [1, 2, 3]
    g: (function(i64) -> i64) = ident
    print(app(f: g, x: 20).to_str())
    print(ns.map(g).len().to_str())
```

Output:

```
20
3
```

# choice_points

1. **Line 11, where `app`'s `A` could be fixed by `x: 20`.** One could argue that `x: 20` fixes `app`'s `A` as `i64` (the literal defaults to `i64` because the parameter asks for no type), and that this then makes `f`'s type concrete, `(function(i64) -> i64)`, which instantiates `ident`. I read "a generic function's parameter asks for none" as forbidding exactly that: the expected type does not flow from a generic parameter to its argument, so `ident`'s `A` is never fixed. If the other reading held, line 11 would be accepted and print `20`, and only line 12 would be in question.
2. **Line 12, `ns.map(ident)`.** `map`'s `A` is `i64` from `ns`. Under a unifying reading, `ident` would become `(function(i64) -> i64)` and `B` would be `i64`. Under my reading, `B` has no source: `ident`'s signature is generic, so it does not give `B` the way `double`'s concrete signature does in the spec's example, and the `.len()` receiver asks for nothing. Under the other reading the whole original program would be accepted and print `20` then `3`.
3. **Form of the fix.** I added one annotated binding `g: (function(i64) -> i64) = ident` and used it on both lines. An alternative is a non-generic `function ident_i64(x: i64) -> i64`, which gives the same output with more text. I chose the binding because it is the smaller change and keeps `ident` generic. It relies on an annotated binding being a context that asks for a type, which the `b: u8 @ 255` example establishes for literals and which I extend to function values.
4. **Named arguments in `app(f: ..., x: ...)`.** The two parameters have different types, so names are not mandatory. The `Arg` production makes them optional, and I read that as allowed. They are kept.

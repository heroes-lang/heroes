`geom.hero` (changed):

```
# Points and rectangles.

record Point
    x: f64
    y: f64

record Rect
    corner: Point
    width: f64
    height: f64

function dist2(a: Point, b: Point) -> f64
    dx = a.x - b.x
    dy = a.y - b.y
    return dx * dx + dy * dy

# The area of `r`: its width times its height.
function area(r: Rect) -> f64
    return r.width * r.height
```

```
function main()
```

# choice_points

- **Parameter name.** The call site in `main.hero` writes `geom.area(r: r)`, so the parameter is named `r`. The specification makes names mandatory only when two parameters share a type (section 9). The grammar `Arg = [ ident ":" ] ...` allows a name on any argument, so I read it as allowed here. It does not say outright that a name has to match the parameter, but that is the only sensible reading. Any other name, such as `rect`, would probably make the call in `main.hero` fail to compile.
- **Return type.** I chose `f64`, because the fields are `f64` and section 3 forbids implicit conversions. The alternative `f64?` would make `.to_str()` in `main` apply to a fallible value, which does not type-check without `.must()` or a `match`, so `main.hero` would also have to change.
- **Negative or non-finite sizes.** The specification says nothing about whether a `Rect` may have a negative width or height. I return the plain product, so a negative width gives a negative area. The other options were taking the absolute value (no built-in `abs` exists, so it would need an `if`), or failing (which needs `f64?`, as above). Both would add behavior the task does not ask for. A `nan` or `inf` field flows through the multiplication. Floats have no overflow abort to worry about, since section 7's overflow rule applies to integers and too-large floats become `inf` (section 11).
- **Unused field.** `corner` does not affect the area, so `area` does not read it. The unused-binding rule (section 5) covers bindings and parameters, not fields, and `r` itself is used.
- **Doc comment.** I added a `#` comment directly above `area`, which section 1 says documents it, to match the file's header comment. Leaving it out would change nothing at build time.
- **Placement.** I put the function after `dist2`. Declaration order does not matter (section 4).
- **`main.hero`.** I left it as written. `print` takes an `f64` directly (section 11), so `.to_str()` is redundant but legal (UFCS on the built-in `to_str`). Removing it would print the same text.

# confidence

I believe the program builds and prints `12.0`. Section 11 says a float prints with a point or exponent, and `to_str` renders the same way `print` does (section 2). `3.0` and `4.0` take type `f64` from their fields, and `r.width * r.height` is `f64 * f64`, so no types are mixed.

What I am least sure of is the named argument `r: r` on a single-parameter call. The grammar allows it, and the specification never says a name is forbidden where it is not required. Still, it never states that an optional name must equal the parameter's name, and that is what I relied on. A smaller doubt: whether `r` in `main` and the parameter `r` in `geom` could be treated as shadowing. They are in different files and functions, so I do not believe they clash.

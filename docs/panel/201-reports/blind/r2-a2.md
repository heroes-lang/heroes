`geom.hero`:

```
# Points and rectangles.

record Point
    x: f64
    y: f64

record Rect
    corner: Point
    width: f64
    height: f64

function dist2(a: Point, b: Point) -> f64
    dx = a.x - b.x
    dy = a.y - b.y
    return dx * dx + dy * dy

# The area of `r`: its width times its height.
function area(r: Rect) -> f64
    return r.width * r.height
```

## choice_points

1. **Parameter name.** The spec allows any name. `main.hero` calls `geom.area(r: r)`, so the parameter has to be `r`. The spec makes named arguments mandatory only when two parameters share a type (section 9), but the `Arg` production lets any argument carry a name, so I take it that the name has to match. I chose `r`. Any other name would most likely be a compile error at the call site in `main.hero`. The alternative was to change `main.hero` to call `geom.area(r)`, but that change isn't needed.
2. **Result type.** I chose `f64`, which matches the fields and `dist2`. A fallible `f64?`, failing on a negative width or height, would break `main.hero`. `.to_str()` would then get a `T?`, and `print` takes only a number, `str` or `bool`, so `main.hero` would need a `.must()` or a `match`. `f32` would need `to_f32` conversions and would print with less precision.
3. **Negative dimensions.** The spec has no `abs` built-in and says nothing about rectangle validity. I return the plain product, so a negative width gives a negative area. The other options were taking the absolute value with an `if`, or failing as in point 2. Either would mean deciding what a negative width means, and the task doesn't ask for that.
4. **Operand order.** I wrote `r.width * r.height`. `r.height * r.width` gives the same result for finite floats, and `inf` or `nan` come out the same either way.
5. **Doc comment.** Section 1 says a comment directly above a declaration documents it. I added one to match the file header's style. Leaving it out changes nothing at compile time.
6. **Test block.** Section 12 lets me add `test "3 by 4" assert area(r: Rect(...)) == 12.0`. I left it out because the task asks only for the function. Adding it would have no effect on ordinary builds.
7. **Placement.** Declaration order never matters (section 4). I put `area` after `dist2`. Putting it anywhere else would behave the same.

## confidence

I believe the program builds and prints `12.0`. The reasons:

- `r` is read, so it is not unused.
- `r.corner` is a field that goes unread, but the unused-binding rule covers bindings and parameters, not fields.
- Both operands of `*` are `f64`.
- `geom.area(r: r).to_str()` is UFCS on an `f64` and gives a `str`, which `print` accepts.
- Using the name `r` in both files is not shadowing, because they are different scopes in different files.

I'm least sure about two things:

- **Naming a lone argument.** The grammar permits `r: r`, but the spec only explicitly requires names in the shared-type case. It never says that a name given elsewhere must match the parameter. I assume it must, which is why the parameter is `r`.
- **Exact print text.** Section 11 says a float prints with a point or exponent and reads back as the same value. That points to `12.0`, but the exact format of `to_str` for 12 is inferred, not stated.

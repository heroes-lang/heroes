### The question

Spec § 13's handler sentence says when a signal handler of C's ends for its thread's callbacks (its return, or a followed `longjmp`, `siglongjmp` or `_longjmp` back into the call its signal interrupted), that a callback on that thread before then may abort, and states the thread's abort and panel 258's stop; it lands once its falsifiers run

### The default today

**Default today:** spec § 13's sentence as it stands, *"A callback called after C left a handler of C's by ... may abort, saying the handler was not seen to end, or that C called it from inside one"*: every clause a *may*, nothing promised, true on every platform the sitting ran.

### Prior art

`docs/panel/262-a-signal-handler-of-cs-ends-at-its-return-or-a-followed-jump-back-and-a-callback-on-its-thread-before-then-may-abort.md`, the historian's report `docs/panel/262-reports/historian.md`; read 2026-11-27 by the synthesis, each link below re-read that day.
- **Reached first by Go**: [os/signal](https://pkg.go.dev/os/signal): where the non-Go code a Go program calls changes no signal handlers or masks, the program behaves as a pure Go program does, and non-Go code that installs a handler must give it the `SA_ONSTACK` flag or the program is likely to crash when the signal arrives.
- **Reached first by POSIX**: [longjmp(), IEEE Std 1003.1-2024](https://pubs.opengroup.org/onlinepubs/9799919799/functions/longjmp.html): `longjmp()` is async-signal-safe, but where it is called from a handler that interrupted a function that is not, every later call to such a function is undefined; the application usage recommends against calling `longjmp()` or `siglongjmp()` from a handler.

# program

```
extern "sys/socket.h"
    constant AF_UNIX: i64
    constant SOCK_STREAM: i64
    function socket(domain: i32, type: i32, protocol: i32) -> i32

extern "shim.h"
    record SockaddrUn tag sockaddr_un
        sun_len: u8
        sun_family: u8
        sun_path: i8[104]
    function connect_un(fd: i32, @addr: SockaddrUn lent, len: u32) -> i32

constant SOCK_PATH: str
    "/tmp/demo.sock"

function main()
    fd = socket(domain: AF_UNIX.to_i32().must(), type: SOCK_STREAM.to_i32().must(), protocol: 0)
    print("socket: ", fd)
    addr: SockaddrUn @ SockaddrUn(sun_len: 106, sun_family: AF_UNIX.to_u8().must(), rest: zero)
    for i in range(from: 0, to: SOCK_PATH.len())
        addr.sun_path[i] @ SOCK_PATH[i].to_i8().must()
    rc = connect_un(fd, @addr, 106)
    print("connect_un: ", rc)
```

How the path's bytes reach `sun_path`: the record is built with `rest: zero`, so all 104 bytes of `sun_path` start as zero. A loop then copies the path one byte at a time. `SOCK_PATH[i]` gives a `u8`, `to_i8().must()` turns it into the field's element type, and `addr.sun_path[i] @ ...` writes it into the mutable binding. Because `addr` is an `@` name passed as `@addr`, C gets the struct with those bytes in it. After the path, `sun_path` holds the 14 bytes of `/tmp/demo.sock` at indices 0 to 13, then zeros at indices 14 to 103, 90 zero bytes in all. Index 14 is the terminating NUL that C expects. Nothing ever writes a byte past index 13, so the zeros all come from `rest: zero`.

# choice_points

1. **Which group holds which declarations.** I put `socket`, `AF_UNIX` and `SOCK_STREAM` in a `"sys/socket.h"` group, and the record and `connect_un` in a `"shim.h"` group. The other choice is to put everything under `"shim.h"`. That only compiles if `<sys/un.h>` pulls in `<sys/socket.h>` (it usually does on Darwin); if it doesn't, clang refuses `socket` and the constants. I added no `link` clause, since these are libc symbols. Adding a wrong `link` would be a link error.

2. **Constant types.** I declared `AF_UNIX` and `SOCK_STREAM` as `i64`, following the spec's `SQLITE_OK: i64` example, and convert with `to_i32().must()` / `to_u8().must()` where they are used. Declaring them `i32` would probably also compile and would make the `socket` conversions unnecessary. But `sun_family` would still need `to_u8`, because there are no implicit width conversions. Passing an `i64` constant straight to an `i32` parameter or a `u8` field without converting is a compile error.

3. **`socket` parameter types and names.** These are `i32` because C says `int`. A parameter must match the header's width and sign, so `i64` is refused. `i16` would be accepted because C converts it exactly, but nothing is gained. All three parameters share a type, so named arguments are required at the call. Calling `socket` positionally is a compile error.

4. **Result widths.** I used `-> i32` for both `socket` and `connect_un`. The spec allows a wider result, so `-> i64` would also compile. But then `fd` would have to be converted back with `to_i32().must()` before it goes to `connect_un`; without that conversion the program fails to compile.

5. **Record name and `tag`.** The header only spells the type as `struct sockaddr_un`, so I wrote `record SockaddrUn tag sockaddr_un`. Writing `record sockaddr_un` with no `tag` would make clang look for a type named `sockaddr_un` without the word struct, which fails. Writing the tag with no fields would declare a handle (`struct sockaddr_un *`), which is a different thing and doesn't match a by-pointer struct parameter.

6. **Field types.** `sun_len: u8` (unsigned char) and `sun_family: u8` (sa_family_t, 8-bit unsigned here) are fixed by the header. For `sun_path` I chose `i8[104]`, because plain `char` is signed on Darwin, including arm64. If `char` were unsigned on the target, `i8[104]` would be refused and `u8[104]` would be right. Then the copy would be `SOCK_PATH[i]` with no conversion. Any size other than 104 is a compile error.

7. **How the struct reaches a `const struct sockaddr_un *`.** I made the parameter `@addr` (pointer semantics: copy in, copy out) and the binding a mutable `addr: SockaddrUn @`. A plain `addr: SockaddrUn` would declare a by-value struct parameter, and clang would refuse it against the pointer. `const` means C writes nothing back, so the copy-out is harmless.

8. **`lent` on `@addr`.** `connect` keeps no pointer to the address, so I marked it `lent`. Without `lent` the program would probably still compile, since an `@` argument is a copy-in/copy-out rather than a `.cstr()`/`.ptr()` lend. If the compiler treats it as a lend, the unmarked version is refused. If it treated `lent` on an `@` parameter as an error, my version would be refused. I think that is unlikely, because the grammar allows it.

9. **Filling `sun_path`.** I used `rest: zero` plus a per-byte loop. The alternative is to name `sun_path` in the construction with a 104-element array literal: 14 path bytes followed by 90 zeros. That does the same thing but is long and easy to get wrong. A literal with the wrong number of elements is a compile error.

10. **`sun_len` value.** I set it to 106, which is `sizeof(struct sockaddr_un)`. `SUN_LEN` (2 + 14 = 16) or 0 would also compile. Darwin's kernel overwrites `sa_len` from the length argument, so the program would behave the same.

11. **`len` argument.** I passed 106, the whole struct. `16` (`SUN_LEN`) would also compile and connect to the same path. A value below 16 would cut the path off and connect to a different (or invalid) address. A value above 106 makes connect fail with `EINVAL`.

12. **Path as a constant.** `SOCK_PATH` is a `str` constant. A local `path = "/tmp/demo.sock"` would behave the same.

13. **Not closing the socket.** I bound no `close`, and the process exits right afterwards, which releases the descriptor. The fd is a plain `i32`, not a handle, so there is no "handle nobody consumes" abort. Binding `close` and leaving its result unused would be a compile error; it would need `_ = close(fd)`.

# confidence

I'm moderately confident it compiles and does the task. It prints `socket: <fd>` (a small non-negative number such as 3) and `connect_un: <rc>`. `rc` is `0` if something is listening on `/tmp/demo.sock`, otherwise `-1` (ENOENT or ECONNREFUSED). The program prints the return value either way and does not treat `-1` as an error.

What I'm least sure of:
- **`connect_un` may not exist as a symbol.** `shim.h` only declares it. If no matching C definition is compiled and linked, the build compiles but fails at link time. Nothing in the spec says the compiler generates one.
- **How an `@` record parameter is passed.** I'm assuming it reaches C as a pointer to the struct, and that `lent` is accepted on it.
- **`i8` versus `u8` for `char`.**
- **Assigning into a fixed-array field element** (`addr.sun_path[i] @ ...`). The `Place` grammar allows it, but the spec never shows it for a group record.

# program

```
extern "sys/utsname.h"
    record Utsname tag utsname
        sysname: i8[256]
        nodename: i8[256]
        release: i8[256]
        version: i8[256]
        machine: i8[256]
    function uname(@buf: Utsname) -> i64

function main()
    buf: Utsname @ Utsname(rest: zero)
    rc = uname(@buf)
    if rc != 0
        print("uname failed")
        exit(code: 1)
    print(buf.sysname.validated_bytes().must())
    print(buf.machine.validated_bytes().must())
```

# choice_points

1. **Element type of the `char[256]` fields: `i8[256]` vs `u8[256]`.** Section 13 says a field is declared at the header's own width and sign, and one that disagrees is refused. Plain `char` is signed on Darwin (the headers come from "this machine", and the environment is macOS), so I chose `i8`. If the compiler instead treats plain `char` as unsigned, or as a "byte" that only `u8` matches, `i8` is a compile error and `u8` would be right. The other way round, `u8` against signed `char` is a compile error. Both versions run the same once accepted.

2. **Record name and `tag`.** The header has only `struct utsname`, no typedef. Section 13 says the record takes the struct's name "unless the header writes it after the word struct, which `tag` gives". I read that as making `tag utsname` required here, so I named the record `Utsname` with `tag utsname`. Leaving out `tag` (for example `record utsname` with no tag) might also be accepted under another reading. Either way, `record Utsname` without a tag would be a compile error, because clang would find no struct named `Utsname`.

3. **Declaring all fields vs `partial`.** I declared all five fields. `record Utsname tag utsname partial` with only `sysname` and `machine` would also compile and do the same thing, since `partial` keeps C's size. The only cost would be that such a record cannot be compared. Leaving out a field without `partial` is a compile error.

4. **How the struct pointer is passed: `@buf: Utsname` (out-parameter).** Section 13 says a C out-parameter is an `@` parameter. The alternative would be a `ptr` parameter, but nothing in the language gives a pointer to a whole record (`f.ptr()` lends only a field, and needs `counted_by`), so that approach would not compile. I did not add `lent`. The sqlite example's `@out` has none, and `lent` is described for lends (`cstr()`, `ptr()`), not for `@` copy-in/copy-out. If the compiler counts an `@` record argument as a lend that needs `lent`, leaving it out is a compile error, and `@buf: Utsname lent` would be the fix.

5. **Result type `-> i64` vs `-> i32`.** C returns `int`, and "a result may be wider than C's", so both compile. With `i32`, the literal `0` in `rc != 0` simply becomes an `i32`. The behaviour is the same.

6. **Initialising the buffer: `Utsname(rest: zero)`.** The only other option is to write all five fields out as 256-element array literals. That is legal but impractical, and it behaves the same. A `@` binding is required, both because the declaration needs an initialiser and because "C writes back ... only where the binding is a `@` name". Using `buf = ...` (immutable) would be refused at `uname(@buf)`.

7. **Turning the bytes into text: `validated_bytes()` then `.must()`.** `validated_bytes()` reads up to the first zero and gives a `str?`. I used `.must()`, which aborts on invalid UTF-8. A `match` that prints `e.msg` would compile too, and would print an error line instead of aborting on non-text names. Using `?` would be a compile error, because `main` returns nothing, not a fallible type. Passing the `str?` straight to `print` would be a compile error as well, since `print` takes only numbers, `str` and `bool`.

8. **Handling the `uname` result.** The result has to be used ("a line that computes a value must use it"), and `_ = uname(@buf)` would also compile. I check it, print a message and `exit(code: 1)` when it fails. The spec gives no way to write to stderr, so the message goes to standard output. Without the check, a failure would print two empty lines (the buffer is zeroed).

9. **Which field is "the hardware type".** I used `machine` (the field `uname -m` reports). No other field fits.

# confidence

I'm fairly confident that this compiles and prints the system name (for example `Darwin`) and then the machine type (for example `arm64`) on two lines. I'm least sure about choice point 1, whether plain `char` has to be `i8` or `u8`. After that comes choice point 4, whether an `@` record out-parameter also needs `lent`. A smaller question is whether a construction may consist of `rest: zero` alone.

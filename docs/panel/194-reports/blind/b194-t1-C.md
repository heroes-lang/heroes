# choice_points

1. **Record name versus C tag.** The header only writes `struct utsname`, so a record has to either be named `utsname` or use `tag utsname`. I chose `record Utsname tag utsname`. The alternative, `record utsname` with no tag, should compile the same way, since section 13 says the name defaults to the struct's name. What would be a compile error is a different name with no `tag`, for example `record Utsname` alone, because clang would not find `struct Utsname`.

2. **All fields or `partial`.** I listed all five fields, so the record has C's full layout. The other option, `record Utsname tag utsname partial` with only `sysname` and `machine`, should also compile and keep C's size. It would also need one fewer `ZEROS` argument per field left out. I chose the full form so that clang checks every field against the header. Leaving out a field without `partial` would be a compile error.

3. **Field element type.** C's `char` is `i8`, as section 13 says, so each field is `i8[256]`. Writing `u8[256]` would break the rule that a field must match the header's width and sign, so it would be a compile error. The size has to be the literal `256`, because the `Type` grammar only allows an `integer` inside the brackets. `_SYS_NAMELEN` would be a parse error there.

4. **Pointer parameter as `@` versus `ptr`.** `struct utsname *` is an out-parameter, so I declared it `@buf: Utsname` and call it as `uname(@u)`. A `buf: ptr` parameter with a `.ptr()` lend does not fit: `.ptr()` lends a field and needs `counted_by`, and nothing lends a whole record. Declaring it `buf: Utsname` without `@` would say C takes the struct by value, and clang would reject that against the header.

5. **`lent` on the parameter.** I left it out. `lent` is about lends (`.cstr()`, `.ptr()`), and an `@` record argument is copy-in/copy-out, not a lend. The grammar would accept `@buf: Utsname lent`. It would either be accepted with no visible effect or be rejected as a mark on something that is not a lend. I'm not sure which.

6. **Result width.** C returns `int`. Section 13 allows a result to be wider, so I wrote `-> i64`, following the `sqlite3_open` example. `-> i32` would also compile. Then `rc` would be an `i32`, and the literal `0` in `rc != 0` would take that type, so behaviour is the same. A narrower type such as `i16` would be refused.

7. **No `link`.** `uname` is in the C library, so the group names no library. Adding `link "c"` would probably still compile and link. I can't be sure, because the spec does not say how a redundant library is handled.

8. **Building the initial value.** Every binding must be initialised, and a mutable record has to be built by naming all its fields. Fixed arrays are built with a literal that has exactly as many elements as the type says. To avoid writing 1280 zeros, I wrote one `constant ZEROS: i8[256]`, which section 4 allows because its body uses only literals, and reused it five times. Writing the literal inline five times would do the same thing. Using fewer or more than 256 elements would be a compile error. A `range(...)`-built `[i64]` would also be a compile error: it is a dynamic array and the wrong element type.

9. **Layout of the 256-element literal.** Section 10 says a container literal "separates elements by newline across lines and by comma on one". I put one element per line, which fits that reading exactly. The other layout would be several comma-separated zeros per line with each line ending in `,`. The bracket rules seem to allow it, since a line ending in `,` simply continues. But the prose could be read as forbidding mixed separators, and then it would be a compile error. I chose the reading that is clearly allowed, at the cost of length.

10. **Turning the bytes into text.** `f.validated_bytes()` reads a byte field up to its first zero and gives a `str?`. I extract it with `.must()`, which aborts with a reason if the bytes are not UTF-8. Using `.default("?")` or a `match` would compile and print a fallback or a custom error instead of aborting. Calling `.cstr()` or `.validated()` on the field would be a compile error, because nothing lends a field to `cstr` and `validated` is for `cstr` values.

11. **Handling uname's failure.** If `rc != 0`, the program prints a message and calls `exit(code: 1)`. Leaving the check out would make `rc` an unused binding, which is a compile error. Writing `_ = uname(@u)` would compile but quietly print whatever is in the zeroed buffer, which is empty lines, if the call failed. I print the failure message with `print`, which goes to standard output, because the spec gives no way to write to standard error.

12. **Which field is "hardware type".** I print `machine`, which is POSIX's hardware identifier (for example `arm64` or `x86_64`). Printing `version` or `release` would compile but print something other than what the task asks for.

# confidence

I'm fairly confident it compiles and prints the system name (for example `Darwin`) and then the machine type (for example `arm64`), each on its own line. I could only check it by reading against the spec. I have not compiled or run it, since no compiler was available.

What I'm least sure of:
- Whether a fixed-array type such as `i8[256]` is allowed as the type of a top-level `constant` outside an extern group. The grammar allows it, but the prose only shows numeric constants. If it is refused, the fix is to write the 256-element literal inline for each field.
- Whether a `validated_bytes()` call can go directly on `u.sysname` when `u` is a mutable record, rather than on a field of an immutable binding.
- Whether an `@` record parameter in an extern needs `lent` (choice 5).
- The literal layout (choice 9). One element per line is the safest reading.

# program

```
extern "pthread.h"
    record Mutex tag _opaque_pthread_mutex_t
        __sig: i64
        __opaque: i8[56]
    function pthread_mutex_init(@m: Mutex, attr: ptr) -> i32
    function pthread_mutex_lock(@m: Mutex) -> i32
    function pthread_mutex_unlock(@m: Mutex) -> i32

# Prints the mutex's 64 bytes: the signature word, then the 56 opaque bytes.
function show(m: Mutex)
    parts: [str] @ []
    for i in range(from: 0, to: 56)
        parts @ parts.push(to_str(m.__opaque[i]))
    print("__sig: ", m.__sig)
    print("__opaque: ", join(parts, " "))

function main()
    m: Mutex @ Mutex(__sig: 0, rest: zero)
    init_result = pthread_mutex_init(@m, nullptr)
    print("pthread_mutex_init: ", init_result)
    show(m)
    counter: i64 @ 0
    for i in range(from: 0, to: 3)
        lock_result = pthread_mutex_lock(@m)
        counter @ counter + 1
        unlock_result = pthread_mutex_unlock(@m)
        print("round ", i + 1, ": lock ", lock_result, ", counter ", counter, ", unlock ", unlock_result)
```

Expected output shape: `pthread_mutex_init: 0`, the two lines of bytes, then
`round 1: lock 0, counter 1, unlock 0`, and the same for rounds 2 and 3 with
counter 2 and 3.

**The mutex's bytes before its first lock.** The program builds the record with
`rest: zero`, so before `pthread_mutex_init` all 64 bytes are zero. It then calls
`pthread_mutex_init(@m, nullptr)`, so before the first lock the bytes are whatever
that call wrote. `show(m)` prints them, so the run itself answers the question.
On Darwin I expect `__sig` to be `_PTHREAD_MUTEX_SIG` (0x4D555458, ASCII "MUTX",
printed in decimal as 1297437784). I expect the opaque bytes to hold the default
attributes (normal type, no priority protocol, process-private) and zeroed lock
and sequence words. That expectation comes from my general knowledge of Apple's
libpthread and not from `headers.txt`, which is why the program prints the bytes
instead of assuming them.

**Why that is a valid mutex on this machine.** On this machine (Darwin, per
`headers.txt`) a `pthread_mutex_t` is not just a zeroed lock word. It is
`{ long __sig; char __opaque[56]; }`, and `pthread_mutex_lock` checks `__sig`
before doing anything else. All zeros (signature 0) is *not* a valid mutex here,
unlike glibc on Linux, where an all-zero mutex matches `PTHREAD_MUTEX_INITIALIZER`.
Locking a zeroed Darwin mutex returns `EINVAL` (22). There are only two ways to
get a valid mutex. One is the static initializer
`{_PTHREAD_MUTEX_SIG_init, {0}}`, whose signature the library recognizes and
initializes lazily on first lock. The other is `pthread_mutex_init`, which
writes the full signature and the attribute bits. The program uses
`pthread_mutex_init` with a null `attr`, which the header comment allows and
which gives default attributes. So the bytes before the first lock carry the
initialized signature, and the mutex is valid. A return of 0 from init and from
every lock/unlock confirms this at run time.

# choice_points

1. **How the mutex is made.** Chosen: zero it with `rest: zero`, then call
   `pthread_mutex_init(@m, nullptr)`.
   - Alternative A, the static initializer: `Mutex(__sig: 0x32AAABA7, rest: zero)`
     with no init call. It compiles. It would work only if 0x32AAABA7 really is
     `_PTHREAD_MUTEX_SIG_init`. That value is not in `headers.txt` (it is my
     recollection), so a wrong literal would compile and then every lock would
     return `EINVAL`.
   - Alternative B, the same thing with the value taken from the header:
     `constant _PTHREAD_MUTEX_SIG_init: i64` in the group. The spec says
     "Constants use SCREAMING_CASE", and this name has lowercase `init` and a
     leading underscore, so it is likely a compile error.
   - Alternative C, zeroing only: `rest: zero` with no init. It compiles, and on
     Darwin every lock and unlock returns 22 (`EINVAL`) while the counter still
     reaches 3, because the counter increment does not depend on the result.
2. **Width and sign of `char __opaque[56]`.** Chosen: `i8[56]`, because plain
   `char` is signed on Darwin (both x86_64 and arm64). `u8[56]` would disagree in
   sign with the header, and the spec says such a field "is refused", so that is
   a compile error. `i64[7]` or any other shape is also refused.
3. **`long __sig`.** Chosen: `i64` (LP64). `i32` would be refused as a field of
   the wrong width.
4. **Record name and tag.** Chosen: `record Mutex tag _opaque_pthread_mutex_t`.
   Alternative: `record pthread_mutex_t` with no tag, naming the typedef. I
   believe that compiles too, but the spec only describes the struct word and
   `tag`, so I chose the explicit tag. A tag with no fields would instead make a
   handle (`struct ... *`), which is the wrong type for these calls and would be
   refused or would misbehave.
5. **How the `pthread_mutex_t *` parameter is passed.** Chosen: an `@` parameter
   of the record type (`@m: Mutex`), the spec's form for a C pointer that C
   writes through. Alternative: `m: ptr` with `m.ptr()`. That is refused,
   because `f.ptr()` lends only a field and needs `counted_by`, and a record
   binding is not that.
6. **`const void *attr`.** Chosen: `attr: ptr`, with `nullptr` passed.
   Alternative: a handle `record Attr tag void` would also take `nullptr`, but
   it adds nothing. Passing a real attribute object is out of scope.
7. **Result type of the `int` returns.** Chosen: `i32`, C's own width.
   Alternative: `i64` is allowed ("a result may be wider than C's"), compiles,
   and prints the same.
8. **No ownership words** (`acquires`, `consumes` and so on). These words mark
   only values reaching a handle, and the mutex is a by-value record, so adding
   them would be a compile error. There is also no `pthread_mutex_destroy`,
   because `headers.txt` does not declare it. On Darwin a default mutex holds no
   resources, so nothing leaks.
9. **Loop variable.** Chosen: `for i in range(...)` with `i` used in the print.
   Alternative: `for _ in ...` may not parse, because `For` takes an `ident` and
   the grammar treats `_` separately. An unused `i` would be a compile error.
10. **Iterating the fixed array.** Chosen: index `m.__opaque[i]` over
    `range(from: 0, to: 56)`. Alternative: `for b in m.__opaque` might also
    compile, but the spec does not say a fixed array is iterable.
11. **Printing results.** Chosen: print each call's result, without aborting on
    a nonzero one, so a failure is visible instead of hidden.
    Alternative: `assert lock_result == 0` would stop at the first failure.

# confidence

I believe it compiles and does what the task asks: it prints the init result,
the mutex's bytes before the first lock, and then for each of the three rounds
the lock result, the counter (1, 2, 3) and the unlock result. I expect all the
results to be 0.

What I am least sure of:
- **Copy-in/copy-out of `@m`.** The spec defines `@` as copy in, copy out. If
  the compiler passes C a temporary copy at a different address instead of `m`
  itself, the mutex is moved between calls. POSIX does not allow moving a mutex.
  On Darwin, init also records whether the address is 8-byte aligned and places
  its lock words accordingly. Single-threaded use with aligned copies should
  still work, but this is the main risk.
- Whether identifiers beginning with `__` lex as `ident`. They must match the
  header's field names, so there is no alternative spelling.
- Whether `rest: zero` together with a named field is accepted exactly as
  written. I believe it is, from the spec text.
- The exact opaque bytes after init. I gave my expectation above, and the
  program prints the real ones.

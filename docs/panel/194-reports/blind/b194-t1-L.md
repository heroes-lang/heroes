# choice_points

1. **Element type of the `char[256]` fields: `i8[256]` vs `u8[256]`.** Section 13 says a field is declared "at the header's own width and sign", and plain `char` is signed on Darwin (the platform these headers come from), so I wrote `i8`. The other choice, `u8[256]`, compiles only if the compiler treats plain `char` as unsigned or as sign-agnostic; under a strict reading it is refused as a field that disagrees with the header (compile error). The flip side: if the compiler only accepts `u8` arrays as the "field of bytes" that `validated_bytes()` reads, then my `i8` choice is the one that fails to compile.

2. **Record name and `tag`.** The header names the type only as `struct utsname`, so I used `record Utsname tag utsname`. Writing `record utsname` with no `tag` should also compile and work the same way. Writing `record Utsname` without `tag` would be refused, because clang finds no struct named `Utsname`. Writing `record Utsname tag utsname` with no fields would declare a handle (`struct utsname *`) and not the struct, so the program would no longer match the out-parameter and would have no fields to read (compile error).

3. **Full field list vs `partial`.** I declared all five fields. The other choice, `record Utsname tag utsname partial` with only `sysname` and `machine`, would also compile and print the same output, since a partial record keeps C's size. It would also mean I only need to build two fields. The cost is that a partial record cannot be compared, which this program never does.

4. **How the `struct utsname *` parameter is declared.** I wrote it as an `@` out-parameter (`@buf: Utsname`), which is what section 13 says a C out-parameter is, and passed it as `uname(@u)` with `u` a `@` binding so that C's writes come back. The other choices: a non-`@` `buf: Utsname` would pass a struct where C expects a pointer and be refused (compile error), and a `ptr` parameter would have no way to lend a whole record, since `f.ptr()` lends only a field with `counted_by` (compile error). Binding `u` with `=` instead of `@` is a compile error, because only a `@` name can be passed to an `@` parameter.

5. **`lent` on that parameter.** I marked it `lent` because `uname` does not keep the pointer, and the spec says a lend reaches only a parameter declared `lent`. If the compiler does not count passing an `@` record as a lend, then `lent` is just redundant and the program still compiles. Leaving it out would compile and run the same if `@` passing is not a lend, and would be a compile error if it is.

6. **Result width.** C's result is `int`, and I wrote `i32`. Section 13 allows a result wider than C's, so `-> i64` would also compile and behave the same. Something narrower, such as `i16`, would be refused (compile error).

7. **The initial value of the record.** Every binding needs an initial value, records are built by naming every field, and a fixed array is built as a literal with exactly as many elements as the type says. So I wrote one 256-element zero literal, bound it as `zero: i8[256]`, and reused it for all five fields. A literal with any other element count is a compile error. Nothing in the spec builds a fixed array from `range` or `repeat`. I spread the literal over several lines, each ending in `,` so the line continues inside the brackets.

8. **Checking the result of `uname`.** The result must be used anyway, so I compare it with `0` and on failure print a message and call `exit(code: 1)`. Discarding it with `_ = uname(@u)` would also compile, but a failure would then print empty strings instead of reporting an error.

9. **Turning the fields into text.** I used `validated_bytes().must()`, which aborts if the bytes are not UTF-8. A `match` with an `.err` arm that prints `e.code` would compile and differ only in that unlikely case. `validated()` is a compile error here, because it takes a `cstr` and nothing lends a field to `cstr`.

10. **Not declaring `_SYS_NAMELEN`.** It is a `#define` in the header, and the `Type` grammar only accepts an integer literal as an array size, so I wrote `256` directly. Declaring `constant _SYS_NAMELEN: i64` in the group would not help size the array. If the compiler holds group constants to SCREAMING_CASE, the leading underscore might also be refused.

# confidence

I am fairly confident the program compiles and prints the system name (for example `Darwin`) and then the hardware type (for example `arm64`), each on its own line. I am least sure of:

- whether passing a whole record through an `@` out-parameter counts as a lend that needs `lent` (choice 5);
- whether a fixed-array literal may be bound on its own (`zero: i8[256] = [...]`) and then reused, rather than written inside the constructor.

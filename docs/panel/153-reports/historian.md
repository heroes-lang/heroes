## Finding 3 — handing a value to C by pointer without address-of

- **Ada 2022** RM B.3(66–70), Implementation Advice: "An Ada in scalar parameter is passed as a scalar argument"; "An Ada access T parameter, or an Ada out or in out parameter of an elementary type T, is passed as a t* argument"; "An Ada parameter of a record type T, other than an in parameter of a type of convention C_Pass_By_Copy, is passed as a t* argument"; arrays likewise. RM 6.2: elementary types by copy; tagged, task/protected, explicitly limited records by reference; "For other parameters, it is unspecified whether the parameter is passed by copy or by reference." **Ada 83** LRM 6.2 already said: "The language does not define which of these two mechanisms is to be adopted for parameter passing ... The execution of a program is erroneous if its effect depends on which mechanism is selected by the implementation." Verified — https://www.adaic.org/resources/add_content/standards/22rm/html/RM-B-3.html ; https://www.adaic.org/resources/add_content/standards/22rm/html/RM-6-2.html ; http://archive.adaic.com/standards/83lrm/html/lrm-06-02.html (search excerpt; host refused a direct fetch). So Ada's answer to `const struct addrinfo *hints` is: an `in` record parameter **is** a `t*` at the C boundary, with no operator in the source — Heroes' `@hints: AddrInfo` on an in-parameter has a 1983-to-2022 precedent. Which edition added the by-reference list: **unverified**.
- **Free Pascal**: "Contrary to Delphi, no assumptions should be made about how const parameters are passed to the underlying routine. In particular, the assumption that parameters with large size are passed by reference is not correct." Exception: "the stdcall calling convention: for compatibility with COM standards, large const parameters are passed by reference." Hence `constref`, "available as of version 2.5.1 of the compiler". Verified — https://www.freepascal.org/docs-html/ref/refsu67.html. **This is the shipped-then-changed case**: an unspecified mechanism met C/COM and a keyword had to be added.
- **Swift**: in-out is copy-in copy-out in three numbered steps ("When the function is called, the value of the argument is copied ... the copy is modified ... the copy's value is assigned to the original argument"); "As an optimization, when the argument is a value stored at a physical address in memory, the same memory location is used both inside and outside the function body"; "Write your code using the model given by copy-in copy-out, without depending on the call-by-reference optimization". `&x` bridges to `UnsafePointer<T>`: "The pointer created through implicit bridging of an instance or of an array's elements is only valid during the execution of the called function." Verified — https://raw.githubusercontent.com/swiftlang/swift-book/main/TSPL.docc/ReferenceManual/Declarations.md ; UnsafePointer.swift above. Swift **kept** the model; no reversal found.
- **Zig**: "Zig may choose to copy and pass by value, or pass by reference, whichever way Zig decides will be faster." Issue #5973 "eliminate hidden pass-by-reference footguns", opened 2020-08-01, labelled accepted, now closed (closing comment **unverified**, page did not load); a Ziggit thread of 2024-09-30 reports the plan: "PRO in its current form will cease to exist" (secondary). Verified/secondary — https://github.com/ziglang/zig/issues/5973 ; https://ziggit.dev/t/plan-to-address-attack-of-the-killer-features-parameter-reference-optimization-aliasing-issue-just-dropped/6199. **Second shipped-then-changed case**: compiler-chosen reference passing produced aliasing bugs.
- **Nim**: "var parameters are passed by reference to the procedure. This means that the parameter is an alias to the argument." `a4: var ptr AddrInfo` is the `**res` out-parameter; `hints` is `ptr AddrInfo`, so Nim's caller writes `addr` — Nim has address-of. Verified — manual and `posix.nim` above.
- **Python ctypes** 3.14.7: `byref(obj)` "Returns a light-weight pointer to obj ... corresponds to this C code: (((char *)&obj) + offset) ... The returned object can only be used as a foreign function call parameter." Verified — https://docs.python.org/3/library/ctypes.html. Address-of without an operator, scoped to the call: Heroes' `@` shape.
- **JNA**: a `Structure` argument is `struct*`, auto-written before and auto-read after the call — copy-in/copy-out over native memory, 5.17.0 javadoc above. Verified.

## Finding 5 — what the null read costs

- **Oberon**: emitted check, `IF check THEN Trap(EQ, 4)`; `Trap` emits one `BLR` conditional instruction; switchable by `check`. Verified (ORG.Mod above). Trap-4 message text: **unverified** — `System.Mod` (JG 3.10.90 / NW 12.10.93 / NW 20.6.2016) prints only `"TRAP"; Texts.WriteInt(W, w, 4)`, https://people.inf.ethz.ch/wirth/ProjectOberon/Sources/System.Mod.txt.
- **Go**: the hardware pays. Runtime `sigpanic`: `if (gp.sigcode0 == 0 || gp.sigcode0 == _SEGV_MAPERR || gp.sigcode0 == _SEGV_ACCERR) && gp.sigcode1 < 0x1000 { panicmem() }`. Compiler: `const minZeroPage = 4096` — "All platforms are guaranteed to fault if we load/store to anything smaller than this address."; `nilcheckelim` "eliminates unnecessary nil checks", `nilcheckelim2` "Runs after lowering and scheduling." So a field read within 4096 bytes of the pointer costs zero emitted instructions for the check. Verified — https://raw.githubusercontent.com/golang/go/master/src/runtime/signal_unix.go ; https://go.dev/src/cmd/compile/internal/ssa/nilcheck.go.
- **Zig**: `*T` cannot be null, so a plain pointer read carries no check; the check is at `.?` unwrap, on in Debug/ReleaseSafe, off in ReleaseFast/ReleaseSmall; `[*c]T` null dereference "safety-checked Illegal Behavior on non-freestanding targets" (mechanism unverified). Verified as stated.
- **Ada**: `Access_Check` — "When evaluating a dereference (explicit or implicit), check that the value of the name is not null."; `pragma Suppress` "gives permission to an implementation to omit the named check"; "If a given check has been suppressed, and the corresponding error situation occurs, the execution of the program is erroneous." Verified — https://www.adaic.org/resources/add_content/standards/22rm/html/RM-11-5.html.
- **Nim**: fatal runtime error, defect only with the `segfaults` module — so the fault is hardware-paid (this last step is my inference from the two quoted sentences, not a stated fact).
- A stated cost in cycles or percent: **not found** in any of the five sources above.

## argument

Every language in Heroes' own line after Modula-2 reads a field through a pointer with the dot alone and stops on null: Oberon 1988 to 2016, Ada 1983 to 2022, Go, Nim, Zig. Five of eight surveyed designs do it; the three that do not (Modula-2, Rust raw pointers, Swift) are the ones that expose the pointer itself. Route A is that tradition with the word Heroes already needs. Route B's copy-out exists (JNA `read()`, Rust `ptr::read`) but always beside field access, and no system forbids the pointer and value types of one struct coexisting. The two shipped-then-changed cases (Free Pascal `constref`, Zig #5973) both punish an *unspecified* passing mechanism, so whatever `@` on an in-parameter means, the spec must say it.

## condition

My reading changes if the panel finds (a) a language that had implicit field dereference and removed it, (b) a system where copy-out is the *only* read of a pointed-at struct and lasted a decade, or (c) a language Report whose worked example was corrected because readers copied it. Searched for all three; found none.

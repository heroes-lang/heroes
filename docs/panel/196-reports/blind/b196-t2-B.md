```
extern "math.h"
    function frexp(x: f64, @exp: i32) -> f64

function main()
    e: i32 @ 0
    _ = frexp(8.0, @e)
    print(e)
```

Expected output: `4` (8.0 is 0.5 times 2 to the 4th).

# choice_points

1. **Extern group with no `link`.** The task says nothing needs linking, and section 13 makes `link` optional ("when the symbols need one"). I wrote `extern "math.h"` on its own. Adding `link "m"` would most likely still compile and print `4` on systems that have libm. On a system with no such library, the link step would fail.

2. **Type of the out-parameter.** C has `int *`. Section 13 says what an out-parameter points at "is held to the same width and sign", so I declared `@exp: i32`. The "C converts exactly" exception covers by-value parameters only, not pointees. So `@exp: i64` or `@exp: i16` would be a compile error (refused against the header).

3. **Type of the first parameter and of the result.** C has `double`, so I used `x: f64` and `-> f64`. `x: f32` would be refused, because a parameter must match C's width. A result "may be wider than C's", but nothing is wider than `f64`, and `-> f32` would be narrower and refused by the clang check.

4. **What to do with the returned mantissa.** A line that computes a value must use it. If I wrote `m = frexp(8.0, @e)` and never read `m`, that would be a compile error (unused binding). Writing `frexp(8.0, @e)` as a bare statement would also be a compile error, because the value is neither bound nor discarded. I discarded it with `_ =`, which is allowed because the type is `f64`, not `()` or a `T?`. Binding it and printing it as well would compile but would print an extra line (`0.5`).

5. **Declaring the cell for the exponent.** An `@` argument needs a mutable name, and every binding must be initialised, so I wrote `e: i32 @ 0`. The type is required on a mutable declaration. `e = 0` (immutable) could not be passed as `@e`, which is a compile error. `e: i64 @ 0` would be a type mismatch against `@exp: i32`, also a compile error. The initial value is overwritten by C, so any other `i32` value would give the same output.

6. **Positional or named arguments.** The two parameters have different types (`f64` and `i32`), so names are not required. I passed them by position. `frexp(x: 8.0, @exp: e)` should behave the same, though the spec only explicitly shows named arguments where they are mandatory. In `Arg = [ ident ":" ] [ "@" ] Expression`, the `@` goes on the expression, so it would be written `exp: @e`. Writing `@exp: e` would be a parse error under that grammar.

7. **Parameter names in the extern declaration.** C gives no names, so `x` and `exp` are my choices. They do not reach any call site, because the call is positional. The spec does not say whether the unused-parameter rule applies to a body-less extern function. I assumed it does not, since it has no body to use them in.

8. **Printing `i32` directly.** `print` takes any number, so `print(e)` prints `4`. Converting first with `e.to_i64()` would give a `i64?`, which would need `.must()`. Without it, `print` would be refused because a fallible value is not a number.

9. **The `8.0` literal.** It takes `f64` from the parameter type. Writing `8` would be an integer literal given where `f64` is required, which is a compile error because there are no implicit conversions.

# confidence

I am fairly confident that the program compiles and prints `4`. `frexp(8.0)` returns 0.5 and stores 4, and the declarations match the header exactly. These are the things I am least sure of:
- Whether `_ = f(...)` is fully accepted when the call also writes through an `@` argument. I believe it is, since only `()` and `T?` values are refused.
- Whether parameter names in an extern declaration with no body could ever trigger the unused-parameter error.
- Whether a platform would need `libm` linked explicitly, despite the task saying nothing needs linking.

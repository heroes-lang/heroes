```
# Prints the SHA-256 digest of the three bytes `abc` as lowercase hex.

extern "sha256_abc.h" package "libcrypto"
    constant SHA256_DIGEST_LENGTH: i64
    record Sha256Digest tag sha256_digest
        md: u8[32]
    function sha256_into(data: cstr lent, data_len: u64, md: ptr counted_by md_len lent, md_len: u64) -> i32

function main()
    digest: Sha256Digest @ Sha256Digest(rest: zero)
    status = sha256_into(data: "abc".cstr(),
        data_len: 3,
        md: digest.md.ptr(),
        md_len: SHA256_DIGEST_LENGTH.to_u64().must())
    if status != 1
        print("sha256 failed")
        exit(code: 1)
    parts: [str] @ []
    for i in range(from: 0, to: SHA256_DIGEST_LENGTH)
        byte = digest.md[i].to_i64().must()
        parts @ parts.push(hex_digit(byte / 16))
        parts @ parts.push(hex_digit(byte % 16))
    print(parts.join(""))

function hex_digit(n: i64) -> str
    return "0123456789abcdef".slice(from: n, to: n + 1)
```

`sha256_abc.h`, beside the program:

```c
#ifndef SHA256_ABC_H
#define SHA256_ABC_H

#include <stddef.h>
#include <openssl/sha.h>

/* A buffer for one SHA-256 digest, so the program can lend its field to C. */
typedef struct sha256_digest {
    unsigned char md[SHA256_DIGEST_LENGTH];
} sha256_digest;

/* SHA256() with the output extent passed beside the output buffer.
   Returns 1 on success, 0 when md is too small or OpenSSL fails. */
static inline int sha256_into(const char *data, size_t data_len,
                              unsigned char *md, size_t md_len)
{
    if (md_len < SHA256_DIGEST_LENGTH)
        return 0;
    return SHA256((const unsigned char *)data, data_len, md) != NULL;
}

#endif
```

# choice_points

1. **How to get 32 digest bytes out of C.** The spec gives one way to let C write into memory the program can read: `f.ptr()` lends a record field to a `ptr` parameter declared `counted_by n`, where `n` is a sibling parameter. Neither `SHA256` nor `SHA256_Final` has a parameter that gives the size of `md`, and a group record has to be a struct from the header. So I wrote my own header with a struct `sha256_digest` holding `unsigned char md[32]`, and a `static inline` wrapper `sha256_into` that takes `md_len`. The alternatives:
   - Declare `SHA256` directly with `md: ptr`. With no `counted_by`, `digest.md.ptr()` is refused, a compile error. Passing `nullptr` makes OpenSSL use its static buffer, but the program gets back a `ptr` it cannot read.
   - Declare `md` as `counted_by n` against the input length (3). That is probably accepted because 3 is less than 32, but it tells the compiler the wrong extent while C writes 32 bytes.
   - Declare the result of `SHA256` as `cstr` and call `validated()`. This compiles, but the digest has a zero byte (`...f2 00 15 ad`), so the read stops early or fails `not_text`.
   - Declare `SHA256_CTX` as a group record (`h: u32[8]`, `Nl`, `Nh`, `data: u32[16]`, `num`, `md_len`), call Init/Update/Final, and read `ctx.h` as eight big-endian words. Final still needs an `md` buffer, so the same problem comes back. Reading `h` also depends on OpenSSL not wiping it, which is an internal detail.
2. **Input as `cstr lent`.** `"abc".cstr()` lends the string. I declared the wrapper's parameter as `const char *` so it matches `cstr` exactly. The alternative was a `ptr counted_by data_len` lent from a `u8[3]` field of another header struct. That needs more C code and gives the same result. Leaving out `lent` is a compile error, because a lend reaches only a `lent` parameter.
3. **`md` declared `lent`.** Leaving it out is a compile error for the same reason.
4. **The digest binding is `@`.** The spec says C writes back through a lend only where the binding is an `@` name. With `digest = Sha256Digest(rest: zero)`, the program would compile (or be refused, since the spec does not say which) and print 64 zeros.
5. **`Sha256Digest(rest: zero)` instead of `md: [0, 0, ...]` with 32 elements.** Both compile and behave the same. With 31 or 33 elements, the program does not compile.
6. **Record name via `tag`.** `record Sha256Digest tag sha256_digest` uses the struct tag. Naming the record `sha256_digest` with no `tag` should also work, because the typedef has the same name. Naming a record by something that is neither the typedef nor the tag is a compile error.
7. **Field type `u8[32]`.** It matches `unsigned char[32]`. Writing `i8[32]` or `u8[31]` is refused against the header.
8. **C widths.** `data_len` and `md_len` are `u64` because C says `size_t`. `i64` or `i32` there would be refused. The result is `i32` because C says `int`. `i64` is also allowed, since a result may be wider.
9. **Named arguments.** `data_len` and `md_len` both have type `u64`, so named arguments are required at the call. A positional call is a compile error. I named all four arguments.
10. **`package "libcrypto"` vs `link "crypto"`.** The brief names the package. `link "crypto"` would also need the system to find the OpenSSL headers on its own, and may fail to compile where they are not on the default path.
11. **`md_len` from `SHA256_DIGEST_LENGTH.to_u64().must()` vs the literal `32`.** Same result. The constant also sets the loop bound. A mistyped `md_len` below 32 makes the wrapper return 0, so the program prints `sha256 failed` and exits 1.
12. **Checking the status.** I compare it to 1 and exit with code 1 if it differs. Dropping it with `_ = sha256_into(...)` also compiles, but a failure would then print zeros.
13. **Byte to `i64`.** `to_i64` returns a `T?`, so I used `.must()`, which can never abort for a `u8`. `.default(0)` or a `match` behave the same. Using the `u8` directly with `/ 16` also works, but `slice` wants `i64` indices, so the program would need a conversion anyway.
14. **Hex nibbles.** I used `/ 16` and `% 16`. `>> 4` and `& 15` on the `i64` give the same result (bitwise operators are `i64` only, so they would not work on the raw `u8`).
15. **Building the line.** I pushed parts into a `[str]` and called `join` once. Concatenating with `+` in a loop gives the same output in quadratic time.

# confidence

I believe it compiles and prints `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`. I have not compiled or run it; I only had file reading and writing. What I am least sure of:
- **The `static inline` wrapper.** If the toolchain only checks the header with clang and then links symbols by name instead of compiling C glue that includes the header, `sha256_into` has no symbol and linking fails.
- **Finding the header.** I assume a quoted header in the program's directory is found, and that the package's include flags also reach `openssl/sha.h`.
- **`Sha256Digest(rest: zero)` with no field named.** The spec says this explicitly for unions, but I am inferring it for a plain struct.
- **Indexing a fixed array.** I assume `digest.md[i]` on a fixed-array field indexes it like `[T]`.
- **Deprecation warnings.** If OpenSSL 4.0.3 headers mark `SHA256` deprecated and the build uses `-Werror`, the wrapper fails. The brief says the marks were left out of the excerpt, not that they are absent.

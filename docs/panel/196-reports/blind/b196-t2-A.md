# program

```
extern "math.h"
    function frexp(x: f64, @exp: i32) -> f64

function main()
    e: i32 @ 0
    _ = frexp(8.0, @e)
    print(e)
```

Expected output: `4` (8.0 is 0.5 times 2 to the 4th).

# choice_points

1. **No `link` clause.** The brief says nothing needs linking, and section 13 makes `link` optional ("when the symbols need one"). Alternative: `link "m"` would most likely still compile and print `4` on a system that has libm. On a system with no separate libm it would fail at link time.

2. **The `int *` parameter declared as `@exp: i32`.** Section 13 says a C out-parameter is an `@` parameter, and what it points at is held to the header's own width and sign. C's `int` is `i32`. Alternatives:
   - `@exp: i64` or any other width is refused: a compile error.
   - `exp: ptr` (no `@`) would require passing some address. The language gives a scalar binding no way to produce one, so in practice that is a compile error or an unusable program.

3. **Result type `f64`.** C returns `double`. A result may be wider than C's but not narrower. `f32` would be refused (compile error), and there is nothing wider than `f64`.

4. **Parameter names `x` and `exp`.** The two parameters have different types, so named arguments are not mandatory, and the names are free. Naming them `_` or anything else would compile the same. I passed the arguments positionally. Writing `frexp(x: 8.0, exp: @e)` would also compile and do the same thing.

5. **No `lent` on `@exp`.** Section 13 ties `lent` to lends (`s.cstr()`, `f.ptr()`). An `@` out-parameter on a number is copy-in copy-out, not a lend, so I left `lent` off. Adding `lent` would probably still compile and behave the same. If the compiler counted an `@` scalar as a lend, leaving it off would be a compile error. I consider that unlikely.

6. **Discarding the mantissa with `_ = frexp(...)`.** A line that computes a value must use it (section 5), and the result is a plain `f64`, not a `T?`, so `_` may drop it. Alternatives:
   - Writing the call alone on its line is a compile error.
   - Binding it to a name that is never read is a compile error (unused binding).
   - Binding it and also printing it would compile but print `0.54` instead of only the exponent.

7. **Initial value `0` for `e`.** Every binding must be initialised (section 5). Copy-in passes the value and frexp overwrites it, so any `i32` value gives the same output.

8. **Literal `8.0`.** It takes `f64` from the parameter. Writing `8` would be an integer literal where `f64` is asked for. That is a compile error, because there are no implicit conversions.

# confidence

I am fairly confident that the program compiles and prints `4`. The part I am least sure of is whether the compiler wants anything more on the `@exp: i32` out-parameter, such as `lent`. The spec's example `@out: Db acquires ...` concerns handles, not plain numbers, so it gives no direct precedent for an `int *` out-parameter of a scalar. I am also slightly unsure whether discarding a foreign call's `f64` result with `_ =` draws any FFI-specific objection, but nothing in the spec suggests it does.

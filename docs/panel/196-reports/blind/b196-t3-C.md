# program

```
# Prints this machine's host name, read through gethostname.

extern "unistd.h"
    function gethostname(name: ptr counted_by size lent, size: u64) -> i32

extern "hostbuf.h"
    record HostBuf tag host_buf
        name: i8[256]

function main()
    buf: HostBuf @ HostBuf(rest: zero)
    status = gethostname(name: buf.name.ptr(), size: 256)
    if status != 0
        print("gethostname failed")
        exit(code: 1)
    match buf.name.validated_bytes()
        .ok host => print(host)
        .err e => print(e.msg)
```

# choice_points

1. **How to give C a writable buffer.** The spec offers no `[u8]`-to-pointer lend
   and says nothing lends a field to `cstr`; the only route for C to write bytes
   back is `f.ptr()` on a field of a `@` binding, passed to a `ptr` parameter
   declared `counted_by`. I chose that. Declaring the first parameter as `cstr`
   with `s.cstr()` or `s.lease()` would compile but hand C a copy it may not
   usefully write into (a lend reaches back only through a field), so the program
   would print the original string, not the host name; passing a `[u8]` there is
   a compile error.

2. **Where the fixed array field lives.** Section 13 describes fixed arrays
   (`i8[256]`) as fields of a group's `record`, which must be a struct of the
   header. `unistd.h` has no struct for this, so I wrote `hostbuf.h` with
   `struct host_buf` and declared `HostBuf` in its own `extern` group. The other
   choice, a plain top-level `record` holding `i8[256]`, is not clearly allowed
   (the type grammar admits `T[n]`, but `rest: zero` and the field rules are
   given for group records only); I expect it to be refused or at least to make
   `rest: zero` a compile error.

3. **`tag host_buf` versus a typedef name.** I used a `struct host_buf` and `tag`,
   which the spec spells out. A `typedef struct {...} HostBuf;` with no `tag`
   might also match, since the spec only says the record keeps its name "unless
   the header writes it after the word struct"; if a typedef name does not count,
   that would be a compile error from the clang check.

4. **Field element type `i8` versus `u8`.** C says `char`, and the spec says `i8`
   where it says char for a field; `u8` would be refused as disagreeing with the
   header. Whether `validated_bytes` accepts an `i8` array as "a field of bytes"
   is my assumption; the alternative reading would make that call a compile
   error.

5. **Parameter types.** `size_t` is declared `u64` as the spec states; `i64` or
   `u32` there would be refused. The result `int` is `i32`; `i64` is also
   allowed ("a result may be wider than C's") and would compile and behave the
   same, except the literal `0` in `status != 0` would then be `i64`.

6. **Name of the length parameter.** I called it `size`, not `len`, because `len`
   is a built-in and shadowing is a compile error; if parameter names in an
   `extern` do not count as shadowing, `len` would compile identically.

7. **`lent` on the pointer parameter.** The spec says a lend reaches only a
   parameter declared `lent`; omitting it would be a compile error at the
   `buf.name.ptr()` argument.

8. **Extent passed.** I passed 256, the whole field. Passing more would be
   refused ("one past the field is refused"); passing 255 would compile and
   guarantee a terminating zero, but `validated_bytes` already reads the whole
   field when no zero is present, so 256 is safe.

9. **Constructing the buffer.** `HostBuf(rest: zero)` names no field and zeroes
   all of them. The alternative is writing out a 256-element literal for `name`,
   which compiles and does the same; omitting both is a compile error (every
   field must be named).

10. **Named arguments at the call.** The two parameters differ in type, so names
    are optional; I wrote them. Positional arguments would compile and do the
    same.

11. **Error handling.** A nonzero result prints a message and exits with code 1.
    A non-UTF-8 host name prints the error's message and the program ends with
    code 0; using `.must()` instead would compile and abort in that case. I kept
    the arms inline (one statement each) to avoid the less certain layout of a
    block after `=>`.

12. **Header path.** `extern "hostbuf.h"` assumes the compiler's clang include
    search finds a quoted header in the program's directory. If it does not, the
    group fails to compile; the alternative of a path such as `"./hostbuf.h"`
    would be the fix.

# confidence

I believe the program compiles and prints the host name, with moderate
confidence. Least sure of: whether `validated_bytes` accepts an `i8[256]`
field, whether a group record defined in my own header is found by the
include path, and whether `HostBuf(rest: zero)` with no named field is
accepted. The lend mechanism (`f.ptr()` to a `ptr ... counted_by size lent`
parameter, written back because `buf` is a `@` name) follows the text of
section 13 directly.

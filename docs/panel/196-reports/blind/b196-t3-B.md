# program

```
extern "hostbuf.h"
    record HostBuf tag hostbuf
        name: i8[256]
    function gethostname(name: ptr counted_by namelen lent, namelen: u64) -> i32

function main()
    buf: HostBuf @ HostBuf(rest: zero)
    rc = gethostname(buf.name.ptr(), 256)
    if rc != 0
        print("gethostname failed")
        exit(code: 1)
    match buf.name.validated_bytes()
        .ok host => print(host)
        .err e =>
            print(e.code)
            exit(code: 1)
```

# choice_points

1. **How to give C a writable buffer.** The spec has no `[u8]`-to-`char *` lend for writing; the only way it describes to lend writable bytes is `f.ptr()` on a record field, sent to a `ptr` parameter declared `counted_by`. A group's record has to be a struct in the header, and `unistd.h` has none that fits, so I wrote `hostbuf.h` with `struct hostbuf { char name[256]; }` and included `unistd.h` from it, so clang checks `gethostname` against the real declaration. Other choices: pass `"...".cstr()` or a lease (`cstr`). That might compile, but C would write into a copy that is read-only or never read back, so the program would print nothing useful or crash. If I declared the record in the group without a matching struct in a header, clang would refuse it with a compile error.

2. **Record name and `tag`.** I named the record `HostBuf` and wrote `tag hostbuf`, because the struct in the header is `struct hostbuf`. If I left out `tag`, the compiler would look for a struct named `HostBuf` and fail to compile. Naming the record `hostbuf` with no tag would also work.

3. **Field element type.** I used `i8[256]`, because the spec says "`i8` where it says char". Using `u8[256]` would disagree in sign, and the field would be refused at compile time.

4. **`counted_by` target.** The grammar allows only an ident after `counted_by` (`CParam`), while the prose also shows a number (`counted_by 32`). I named the sibling parameter `namelen`, which fits both the grammar and the header's `_LIBC_COUNT(__namelen)`. Writing `counted_by 256` follows the prose, and it might compile, or the grammar might reject it.

5. **Parameter types.** I declared `namelen: u64` because C has `size_t` there. Using `i64` would be refused at compile time, since the sign disagrees. The buffer is `ptr` because the spec exempts what a `ptr` points at. Declaring it `cstr` would mean a lend that cannot carry a field (it would not compile) and a promise of a zero byte that may not be there.

6. **`lent` on the buffer.** I marked it `lent` because gethostname does not keep the pointer, and the spec says a lend reaches only a parameter declared `lent`. Without it, `buf.name.ptr()` would be refused at compile time.

7. **Result width.** I used `-> i32`, which is C's `int`. The spec also allows a wider result, so `-> i64` would compile and behave the same way.

8. **Mutable binding for the buffer.** I wrote `buf: HostBuf @ ...` because C writes back through the lend only when the binding is an `@` name. With `buf = HostBuf(rest: zero)` the program would still compile, but the name would stay all zeros and it would print an empty line.

9. **Initialising the buffer.** I used `HostBuf(rest: zero)`, which names no field. The other choice is to list all 256 zero elements in `name: [...]`. That gives the same behaviour but is much longer. Leaving out `rest: zero` while naming nothing is a compile error, because every field must be named.

10. **Buffer length passed.** I pass the literal `256`, which equals the field's extent. A larger number would be "one past the field" and refused. A smaller one would compile but could cut long host names short.

11. **Turning bytes into text.** I used `validated_bytes()` on the field, which reads up to the first zero, or the whole field if there is none. It returns `str?`, so I `match` on it. Using `.must()` would compile and abort on non-UTF-8. Using `.default("")` would compile and print an empty line instead. Dropping the result with `_ =` is a compile error.

12. **Error handling.** If gethostname returns nonzero, or the bytes are not text, the program prints a message and calls `exit(code: 1)`. If I printed and fell through instead, the program would compile, then print the empty buffer and exit 0.

13. **Arm binding name.** I named it `host` and not `name`, so it cannot be mistaken for the field or the extern parameter. `name` would most likely compile too, since extern parameter names are not bindings.

# confidence

I believe the program compiles and prints the host name, but I could not compile or run it, because the brief allows only reading and writing files. These are the points I am least sure of:
- whether `counted_by` may name a sibling *parameter*. The prose says "sibling", which could also mean a sibling field. The grammar accepts an ident either way.
- whether the compiler finds `hostbuf.h` in the program's directory. I assume it uses a quoted include relative to the source.
- whether `HostBuf(rest: zero)`, which names no field at all, is accepted. The spec says this outright only for unions.
- whether `validated_bytes()` accepts an `i8[N]` field as "a field of bytes".

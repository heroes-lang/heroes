# program

```
extern "openssl/sha.h" package "libcrypto"
    function SHA256(d: ptr counted_by n lent, n: u64, md: ptr counted_by 32 lent) -> ptr

# Byte buffers of fixed size, so that `f.ptr()` can lend them to C.
extern "abc_buffers.h"
    record Message
        bytes: u8[3]
    record Digest
        bytes: u8[32]

function main()
    message = Message(bytes: ['a', 'b', 'c'])
    digest: Digest @ Digest(rest: zero)
    _ = SHA256(d: message.bytes.ptr(), n: 3, md: digest.bytes.ptr())
    hex = "0123456789abcdef"
    parts: [str] @ []
    for i in range(from: 0, to: 32)
        v = to_i64(digest.bytes[i]).must()
        parts @ parts.push(hex.slice(from: v / 16, to: v / 16 + 1))
        parts @ parts.push(hex.slice(from: v % 16, to: v % 16 + 1))
    print(join(parts, ""))
```

# choice_points

1. **Which OpenSSL entry point to use.** I chose the one-shot `SHA256(d, n, md)`. The other choice, `SHA256_Init`/`SHA256_Update`/`SHA256_Final` with a `record SHA256_CTX` holding all of its fields (`h: u32[8]`, `Nl: u32`, `Nh: u32`, `data: u32[16]`, `num: u32`, `md_len: u32`), would also compile and print the same digest. It needs more declarations, and the headers note says those three are deprecated in 3.0, so they may raise deprecation warnings.
2. **How to pass the input bytes `abc`.** C's parameter is `const unsigned char *`. I declared it `ptr counted_by n lent` and lent a `u8[3]` field with `.ptr()`. The spec exempts "what a ptr points at" from the width and sign check. The other choice, `d: cstr lent` with `"abc".cstr()`, makes `cstr` (C's `char *`) stand against `unsigned char *`. I expect clang's check to refuse that sign mismatch, which would be a compile error. If it were accepted, it would print the same digest.
3. **Where the byte buffers live.** `.ptr()` lends only "a binding's field", and only a group's record has fixed array fields, so the bytes need a C struct. `openssl/sha.h` has no struct of plain bytes. So I wrote my own header (the brief allows this) with `Message` (`unsigned char[3]`) and `Digest` (`unsigned char[32]`), and declared them as `u8[3]` and `u8[32]`, as section 13 requires for C's `unsigned char`. Here are the alternatives:
   - Lending a field of `SHA256_CTX` such as `h: u32[8]` (32 bytes) as `md` would compile. But `counted_by 32` would then count 32 `u32` elements, which goes past the field, so it would be refused or the extent would have to be 8. Reading the bytes back would also mean undoing endianness, so the program would be more fragile.
   - Using a plain `[u8]` with `.ptr()` is not something the spec allows. I would expect a compile error.
   - Declaring the fields `i8` or `u32[...]` would disagree with the header and be refused.
4. **Mutable vs immutable binding for the output.** Section 13 says "C writes back through the lend only where the binding is a `@` name", so `digest` is declared `digest: Digest @ ...`. If it were an immutable `=` binding, the program would still compile, but C's write would not reach it, and it would print 64 zeros.
5. **Initialising the output buffer.** I wrote `Digest(rest: zero)`. The other choice is spelling out 32 zeros: `Digest(bytes: [0, 0, ...])`, with exactly 32 elements. Fewer or more than 32 is a compile error.
6. **The `md` extent.** I wrote `counted_by 32`, a number, which the spec allows where C's extent is fixed. The other choice is declaring `constant SHA256_DIGEST_LENGTH: i64` in the openssl group and naming it there. That gives the same program. A count above 32 would be refused, since it goes one past the field.
7. **The result of `SHA256`.** It returns `unsigned char *`, which I declared `-> ptr` and discarded with `_ =`. Leaving the result off the declaration might be accepted (C returns a pointer the program ignores), or clang's result check might refuse it. Not discarding it would be a compile error, because a line that computes a value must use it.
8. **The type of `n`.** I used `u64`, as the spec says for `size_t`. `i64` or `i32` would be refused as a parameter that disagrees in width or sign.
9. **Named arguments.** `d` and `md` are both `ptr`, so named arguments are mandatory at the call. I named all three. Leaving the names off would be a compile error.
10. **Hex conversion.** Bitwise operators work only on `i64`, so I converted each `u8` with `to_i64(...).must()` and used `/ 16` and `% 16`, which work on any one numeric type. `>>` or `&` on the `u8` itself would be a compile error. Indexing `hex[k]` yields a `u8`, not a `str`, so I used `slice`. Using `hex[k]` in `push` onto a `[str]` would be a type error. I built the line with `join` and not with `+` in the loop. A `+` loop would give the same output.
11. **Package vs link.** The brief names the package `libcrypto`, so the group is `package "libcrypto"`. The other choice, `link "crypto"`, would probably also work on a system with default include and library paths, and would fail to link or find the header otherwise.
12. **No `link`/`package` for my own header.** It declares only types, so there are no symbols to link.

# confidence

I believe the program compiles and prints `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`, but I have not compiled or run it. These are the points I am least sure of:

- Whether the compiler finds `abc_buffers.h` in the program's directory. The spec says where a `use` starts but not where an extern header is looked up. I assumed the compiling file's directory.
- Whether `.ptr()` accepts a field of a record from one group (`abc_buffers.h`) as an argument to a function of another group (`openssl/sha.h`). I read nothing in the spec that forbids this.
- Whether indexing a fixed array field (`digest.bytes[i]`) with an `i64` is allowed. The spec shows indexing on `[T]` and `str` but does not spell it out for `u8[32]`.
- Whether `to_i64` on a `u8` gives a `T?`, as the spec's wording implies, so that `.must()` is required. If it gave a plain `i64`, `.must()` would be a compile error.

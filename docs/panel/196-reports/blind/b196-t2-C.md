# choice_points

1. **Linking.** The extern group names only `"math.h"`, with no `link` or `package`. The task says there is nothing to link. The other choice, `link "m"`, should also compile and run the same on systems that ship a libm. Where no such library exists, it would fail at link time.
2. **Width of the out-parameter.** `@exponent: i32`, because C says `int *` and section 13 holds what an out-parameter points at to the header's width and sign. Choosing `i64` (or `i16`, or any unsigned type) would be refused at compile time. The "C converts exactly" exception covers by-value parameters, not what a pointer points at.
3. **Type of the first parameter and the result.** Both are `f64`, matching C's `double`. Declaring the parameter `f32` would be refused because its width disagrees. A result may be wider than C's, but nothing is wider than `f64`, and `f32` would be refused as narrower.
4. **What to do with the mantissa.** I discard it with `_ = frexp(...)`. It is an `f64`, not a `T?`, so `_` may drop it. Binding it with `m = frexp(...)` and never reading `m` is a compile error (unused binding). Binding it and printing it would compile but also print `0.5`, which goes beyond the task.
5. **Parameter names in the extern.** The names `x` and `exponent` are my own; C's prototype has none. Any other names give the same program. The two parameter types differ, so named arguments are not mandatory, and I call `frexp` positionally. Writing `frexp(x: 8.0, @exponent: e)` would have to use exactly the declared names. A wrong name would be a compile error.
6. **The mutable cell.** `e: i32 @ 0` declares the cell with its type written out, which section 5 requires. The literal `0` takes `i32` from that type. Writing `e = 0` would make an immutable `i64`. Passing it as `@e` would then be a compile error, both because it is not mutable and because its width is wrong.
7. **The literal `8.0`.** It takes `f64` from the parameter type. Writing `8` would be an integer literal in a float position, and with no implicit conversions I expect that to be a compile error.
8. **Printing.** `print(e)` prints an `i32` directly, because `print` takes any number. `print(to_str(e))` or `print(f"{e}")` would print the same `4`.

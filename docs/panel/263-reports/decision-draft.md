    ## Prior art

    `docs/panel/263-no-route-stops-a-callback-overrunning-a-stack-c-allocated-without-a-standing-veto-and-a-handler-switching-inside-the-switch-it-interrupted-aborts.md`, the historian's report `docs/panel/263-reports/historian.md`; read 2026-11-27 by the historian, each link below re-read by nobody since (the synthesis's brief: re-read nothing), so the session that files it re-reads each first.
    - **Reached first by Go**: [runtime/cgocall.go](https://go.dev/src/runtime/cgocall.go): a Go call into C runs the C function on the system stack, `g0`; a call from C back into Go switches from `g0`'s stack to the goroutine's own stack and runs the Go code there; where a C thread's stack bounds are not known, they are taken as from 32 KiB below the stack pointer to just above it.
    - **Reached first by OCaml 5**: [Retrofitting Effect Handlers onto OCaml](https://ar5iv.labs.arxiv.org/html/2104.00250): fibres are allocated on the C heap and each OCaml function's prologue compares the stack pointer with a threshold, the fibre copied to one of twice the size on overflow; C functions have no such checks, so external calls run on the system stack, and callbacks after the first entry from C run on the current fibre.

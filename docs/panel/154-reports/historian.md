# Panel 154 — report of the historian

**Route into the Cyclone, Ada and Wirth rooms came from *Heroes of code* (this project's author). It is named as a route, never as evidence: every claim below carries a primary or vendor source, and what I could not confirm is marked.**
**No shell in this seat (Read/WebSearch/WebFetch only), so every local measurement below is marked `unrun`.**

## Verdict (advisory, this seat has no veto)

- **A, guard every handle argument unconditionally** — **object**
- **B, guard by default plus `accepts_null` opt-out** — **adopt**
- **C, no guard by default plus `not_null` opt-in** — **object**
- **D, infer from `consumes` / `borrows`** — **object, strongly** (would be `refuse` if this seat had a veto: the premise is falsified by two vendor-documented functions)
- **E, compile-time refusal of a statically `nullptr` argument** — **adopt as an addition, object as the resolution**
- **F, sixth route I name: read clang's own `_Nonnull` / `_Nullable` out of the header, guard where unspecified (Kotlin's platform-type rule)** — **adopt as a refinement of B, conditional on the prediction below**
- **G, seventh route I name: compile the emitted C with `-fno-delete-null-pointer-checks` and never emit `__attribute__((nonnull))`** — **adopt as cheap hardening, insufficient alone**

## 1. What the boundary does in each system (brief item 1)

| system | is nullability in the type? | is a check inserted at the C boundary? | verdict |
|---|---|---|---|
| **Nim `importc`** | No for `ptr`. `not nil` exists but is experimental (`{.experimental: "notnil".}`) and "only local symbols are checked" ([manual_experimental](https://nim-lang.org/docs/manual_experimental.html)) | No | **verified** (docs), **unrun** locally |
| **Zig `@cImport`** | Deliberately not at the boundary: translate-c emits `[*c]T`, which "Allows address 0" and "Coerces to other pointer types, as well as Optional Pointers" ([ziglang/zig#6597](https://github.com/ziglang/zig/issues/6597)). Zig's own `*T` cannot be null; `?*T` is the optional | Only **inbound**: coercing a null `[*c]T` to a non-optional pointer is safety-checked illegal behaviour. Nothing checks Zig-to-C **outbound** | **verified** |
| **Go cgo** | No. `*C.struct_x` is nilable | No null check. `cgocheck` polices **Go-pointer-passing/GC rules**, not nullness, and "Go code is permitted to write nil ... to C memory" ([cmd/cgo](https://pkg.go.dev/cmd/cgo)) | **verified** |
| **Rust bindgen** | No: raw `*mut T`. Non-nullness is opt-in via `NonNull<T>`, whose docs state "the pointer must always be non-null, even if the pointer is never dereferenced" ([std::ptr::NonNull](https://doc.rust-lang.org/std/ptr/struct.NonNull.html)) | No. The nomicon's answer is the nullable-pointer optimisation: `Option<&T>`, `Option<Box<T>>`, `Option<extern "C" fn(...)>`, "No `transmute` required!" ([nomicon FFI](https://doc.rust-lang.org/nomicon/ffi.html)) | **verified** |
| **D `extern(C)`** | No non-null pointer type | No. D's `@safe` **allows** `*x` on a null pointer, on the premise that the OS faults first ([pbackus, *What Does Memory Safety Really Mean in D?*](https://pbackus.github.io/blog/what-does-memory-safety-really-mean-in-d.html); [digitalmars.D thread](https://www.digitalmars.com/d/archives/digitalmars/D/safe_code_should_prevent_null_dereferences_345491.html)). Exact spec wording for this: **not found** (searched `dlang.org/spec/memory-safe-d.html`, which does not address null) | **verified for the behaviour, unverified for the spec clause** |
| **Ada `not null access`** | Yes, per parameter | Yes, at the **point of call** (see item 2) | **verified** |
| **Kotlin/Java (closest living analogue)** | Java types arrive as **platform types** `T!`; annotations, when present, produce real nullable/non-null Kotlin types | Yes, by default: "the compiler will emit an assertion upon assignment", plus "an assertion that Kotlin generates to prevent nulls from propagating" ([Calling Java from Kotlin](https://kotlinlang.org/docs/java-interop.html)) | **verified** |
| **Swift/Objective-C** | Unannotated `NSView *` arrives as the implicitly unwrapped optional `NSView!`, which traps on nil use; Xcode 6.3 added `__nullable`/`__nonnull` and `NS_ASSUME_NONNULL_BEGIN/END` ([Swift blog, *Nullability and Objective-C*, 2015](https://developer.apple.com/swift/blog/?id=25), content confirmed via [Use Your Loaf](https://useyourloaf.com/blog/using-nullable-to-annotate-objective-c/) and [miqu.me, 2015-04-17](https://miqu.me/blog/2015/04/17/adopting-nullability-annotations/)) | Yes, by default, on use | **verified** |

**Two relevant precedents nobody in the brief cites.**

- **Cyclone** is the direct ancestor of the design question. `@notnull` pointers "may never be NULL, and thus never need to be checked for NULL upon dereference"; `@nullable` "is present by default"; a dereference of a nullable pointer "will generally be preceded by a NULL-check", and on coercion to `@notnull` "if the value happens to be NULL, then the exception `Null_Exception` is thrown" ([Cyclone manual §3 Pointers](https://www.cs.cornell.edu/Projects/cyclone/online-manual/main-screen003.html); [Dr Dobb's overview](https://www.drdobbs.com/cyclone-a-type-safe-dialect-of-c/184401896)). **Cyclone's polarity is route C at the declaration, route B in effect**, because the check rides the coercion rather than the author's diligence. The USENIX 2002 overhead table is **not retrieved**: [usenix.org PDF](https://www.usenix.org/legacy/publications/library/proceedings/usenix02/full_papers/jim/jim.pdf) returned HTTP 403 and [trevorjim.com mirror](http://trevorjim.com/papers/usenix2002.pdf) refused the connection, so **any number for Cyclone's null-check cost is unverified here**.
- **CVE-2009-1897 is this defect, in the kernel.** "A NULL check would have stopped the attack, but GCC optimized it out on the theory that the pointer could not (by virtue of already having been dereferenced) be NULL" ([LWN, *Fun with NULL pointers, part 2*](https://lwn.net/Articles/342420/)). The repair was a **build flag for the whole project**, `-fno-delete-null-pointer-checks`, added to the kernel Makefile in July 2009 ([lkml patch](https://lkml.iu.edu/hypermail/linux/kernel/0907.2/00705.html); [CVE-2009-1897](https://app.opencve.io/cve/CVE-2009-1897)). Clang gained the flag in 2018 ([D47894](https://reviews.llvm.org/D47894), [D47895](https://reviews.llvm.org/D47895), [RFC](https://discourse.llvm.org/t/rfc-implementing-fno-delete-null-pointer-checks-in-clang/48345)). That is route **G**, and Linux has run on it for seventeen years. It suppresses check **deletion**; whether it also stops clang folding a known-null dereference in an inlined `static inline` body is **unverified and unrun** (no shell).

## 2. Ada 2005 `not null`: what it cost, what it bought (brief item 2)

- Ada 2005's official Rationale: an object of a null-excluding subtype "cannot have the value null"; the exception is `Constraint_Error`; and the check is at the **point of call** ([Rationale §3.2](https://www.adaic.org/resources/add_content/standards/05rat/html/Rat-3-2.html), [§1.3.2](https://www.adaic.org/resources/add_content/standards/05rat/html/Rat-1-3-2.html)). **verified**
- **The trade is stated in Ada's own words**: with the call-site check "within P we would have more efficient code for dereferencing and dispatching at the cost of just one check when the procedure is called" (§3.2). **This is the argument for route B and it is forty years old.** **verified**
- **Ada is also the answer to brief item 4, in the removal direction.** "Anonymous access types in Ada 95 never have null as a value whereas named access types always have null as a value" (§3.2); Ada 2005 gave all access types null, so for a non-controlling parameter without an explicit `not null` you get "`Constraint_Error` being raised within P only when we attempt to do the dereference". **Ada shipped a blanket check on every access parameter and then removed it**, in exchange for uniformity plus an explicit word. **verified**
- Cost as AdaCore states it: "access objects are default-initialized to null, so if you have a 'not null' object (or component) you had better initialize it explicitly, or you will get `Constraint_Error`", which is why the Gem recommends it "for function parameters and results" and calls ideal a non-null default ([Gem #23, *Null Considered Harmful*, 2008-01-14](http://www.adacore.com/blog/ada-gem-23)). **verified**
- **A published measurement of `Access_Check` overhead: not found.** Searched for `Ada Access_Check overhead measured benchmark not null`, `Ada 2005 null exclusion performance`. Also **not found**: whether GNAT performs the null-exclusion check at a call to a `pragma Import`/Convention C subprogram (searched `GNAT "not null" access parameter check imported subprogram pragma Import Convention C`). RM 6.4.1 parameter-passing conversion suggests it does, but that is **an inference, not a measurement**.

## 3. `_Nonnull` / `_Nullable` and audited regions (brief item 3)

- Introduced in **Clang 3.7** ([Attributes in Clang 3.7](https://releases.llvm.org/3.7.0/tools/clang/docs/AttributeReference.html)); the qualifiers are `_Nonnull`, `_Nullable`, `_Null_unspecified`. **verified**
- **The load-bearing distinction for the emitted C**: "Unlike the declaration attribute `nonnull`, the presence of `_Nonnull` does not imply that passing null is undefined behavior: a function is free to consider null undefined behavior or defensively handle null", whereas the `nonnull` attribute makes it UB "which the optimizer may take advantage of to, for example, remove null checks" (quote surfaced from clang's [AttributeReference](https://clang.llvm.org/docs/AttributeReference.html); the direct fetch truncated before the nullability section, so treat the wording as **verified by search excerpt, quotation location unverified**). **Consequence: `_Nonnull` in generated C is safe; `__attribute__((nonnull))` would make the `-O2` half worse.**
- **A runtime check at the boundary already exists in the toolchain and is off by default**: `-fsanitize=nullability-arg`, "Passing null as a function parameter which is annotated with `_Nonnull`", and `-fsanitize=undefined` covers "all of the checks listed above other than ... the `nullability-*` group of checks" ([UBSan docs](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)). The docs' own reason: "while violating nullability does not have undefined behavior, it is often unintentional, so UBSan offers to catch it". **verified.** Exact clang version that added the group: **not found** (searched clang 4.0 release notes, `nullability sanitizer added 2016`).
- Apple's audited regions: `NS_ASSUME_NONNULL_BEGIN`/`END` flip the default inside a region so only `nullable` need be written ([Apple docs](https://developer.apple.com/documentation/foundation/ns_assume_nonnull_end)). **The annotations came from the vendor**: a company-wide effort in the Xcode 6.3 / iOS 9 era (sources above). **The historically decisive detail is that per-pointer opt-in did not scale, so Apple invented a region default.**
- **How much of this Mac's SDK is annotated: unmeasured and unrun** (no shell in this seat). A published coverage figure is **not found** (searched `Apple SDK nullability coverage how many frameworks audited iOS 9`). The command is in the prediction below.

## 4. Shipped a blanket check and removed it, or shipped without and added it (brief item 4)

- **Removed**: **Ada 95 to Ada 2005**, above. **verified.**
- **Removed, in production, for exactly the brief's `freeaddrinfo(NULL)` reason**: the Rust-for-Linux regulator binding changed from `NonNull` to a raw `*mut bindings::regulator` so the pointer may be NULL when `CONFIG_REGULATOR` is off, because that "leverages the C stubs which are designed to handle `NULL` or are no-ops" (Miguel Ojeda, [LKML](https://lkml.iu.edu/2603.3/01231.html)). **verified. This is route A's bill, itemised by a maintainer.**
- **Never shipped**: Nim's default `not nil`. The RFC "made not nil a default", and the tracking issue records that "the 'default not nil' is no longer in the 1.4/1.0 battle plan" ([nim-lang/Nim#6638](https://github.com/nim-lang/Nim/issues/6638), opened 2017-10-31, still open; [PR #3296](https://github.com/nim-lang/Nim/pull/3296)). It survives as two separate experimental features, `notnil` and `strictNotNil` ([strictNotNil docs](https://nim-lang.org/docs/manual_experimental_strictnotnil.html)). **verified.**
- **Relaxed at the boundary for ergonomics, then never tightened**: Zig created `[*c]T` for C interop in 2018 ([ziglang/zig#1059](https://github.com/ziglang/zig/issues/1059), opened 2018-06-05, milestone 0.4.0, closed via PR #1965), with null-capable semantics matching C. The proposal to make C pointers non-optional and have translate-c emit `?[*c]T` was **accepted in October 2020 and is still open** ([#6597](https://github.com/ziglang/zig/issues/6597)). **verified. Moral: the tightening is cheap to agree and expensive to ship once bindings exist. Heroes is before that point, today.**
- **Added, but only under a flag**: CheckJNI "can detect bad pointers, including passing a NULL pointer to a JNI call with a non-nullable argument", on by default in the emulator and off on devices because of its cost ([Android Developers Blog, 2011-07](https://android-developers.googleblog.com/2011/07/debugging-android-jni-with-checkjni.html)). **verified. This is precisely Heroes' `--sanitize` today, and it is the configuration the defect proves insufficient.**
- **Added, different class**: Go's cgo pointer-passing checks, `GODEBUG=cgocheck=1` by default with `GOEXPERIMENT=cgocheck2` for full checking ([cmd/cgo](https://pkg.go.dev/cmd/cgo)). **verified.**
- **A blanket unconditional null check on every pointer argument crossing into C: not found in any system I searched** (Nim, Zig, Go, Rust/bindgen, D, Ada, Kotlin, Swift, Java/JNI, Cyclone). Route A would be, as far as this seat can establish, **without precedent**.

### Route D's premise, falsified

The brief's route D rests on "releases usually accept NULL". Two vendor-documented release functions of identical Heroes shape (`consumes`), opposite rules, neither stated in the header:

- `sqlite3_close(NULL)`: "Calling sqlite3_close() or sqlite3_close_v2() with a NULL pointer argument is a harmless no-op" ([sqlite.org](https://www.sqlite.org/c3ref/close.html)). **verified.**
- `fclose(NULL)`: undefined; glibc segfaults ([comp.std.c thread](https://groups.google.com/g/comp.std.c/c/y4gYqaysdSI), [linuxvox](https://linuxvox.com/blog/why-glibc-s-fclose-null-cause-segmentation-fault-instead-of-returning-error/)). MSVC instead invokes the invalid-parameter handler and sets `EINVAL` ([Microsoft Learn](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/fclose-fcloseall?view=msvc-170)), so **the same call is a no-op, a crash, or an error return depending on the C library**. **verified for the behaviours; the ISO clause number (C11 §7.1.4 "invalid value") is unverified, I could not open the standard text.**
- `free(NULL)`: "If p is NULL, no operation is performed" ([man7 free(3)](https://man7.org/linux/man-pages/man3/free.3.html)). **verified.**

So `consumes` predicts nothing, and an unmarked use position predicts nothing either: `sqlite3_exec`'s callback is a use-shaped parameter where NULL is correct (defect 013's own paragraph). **A mark that is right about ownership is not evidence about nullability.**

### Route E's precedent, and its twenty-year outcome

Route E is `-Wnonnull`, which GCC and clang have warned on for a literal null passed to a `nonnull` parameter for about two decades, and the class stayed open long enough to produce CVE-2009-1897. C# 8's nullable reference types are the same shape one level up: opt-in per file or project, "the runtime behavior of your program is unchanged", "entirely a compile-time feature" with no generated runtime checks ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/csharp/nullable-references)). **verified.** Compile-time refusal of the static witness is worth having and has never, anywhere I searched, closed the class.

### The brief's own `-O0` premise has a known falsifier elsewhere

The shared brief says "a field's offset is smaller than a page in every struct a header can lay out". **D's bug tracker contains the counterexample and the proposed rule**: for `struct { int[10_000] data; ... }` the member access lands beyond the zero page, and the reporter asks the compiler to insert a null check exactly when a member access is known at compile time to reach past one page ([dlang/dmd#17776](https://github.com/dlang/dmd/issues/17776), opened 2016-09-22, closed, P4; resolution **unverified**). A C header can lay out such a struct trivially. **Recommendation: state the `-O0` guarantee as offset-bounded, not universal, and let the empiricist measure the largest field offset in the corpus.**

### Route F, and why it is not free

Kotlin's rule (believe the annotation, assert when the type is unannotated) is implementable here because clang exposes nullability mechanically: `clang_Type_getNullability` returns `CXTypeNullability_NonNull`, `_Nullable`, `_NullableResult`, `_Unspecified`, `_Invalid` ([libclang CXType.cpp](https://github.com/llvm/llvm-project/blob/main/clang/tools/libclang/CXType.cpp), [type API group](https://clang.llvm.org/doxygen/group__CINDEX__TYPES.html)). **verified that the API exists; whether Heroes' pipeline can reach it is unrun.** What is unknown is coverage, which is the prediction.

## 5. The default direction, tallied (brief item 5)

**Safe by default at the boundary (check or trap unless told otherwise): 3.** Kotlin (assertion on crossing into non-null), Swift/Objective-C (unannotated becomes `T!`, traps on use), Ada 95 for access parameters (withdrawn in 2005).
**Nullability in the type but the check only on the inbound edge: 2.** Zig, Cyclone.
**Unsafe by default, programmer's business: 5.** Nim, Go cgo, Rust bindgen, D, C# P/Invoke, plus Ada 2005 unless `not null` is written.
**Check exists but gated behind a flag: 2.** clang `-fsanitize=nullability`, JNI CheckJNI.
**Blanket unconditional outbound check: 0 found.**
The one language that made null absorption the callee's job, Objective-C's message-to-nil returning zero, is documented as having the cost this panel is trying to avoid: "bugs may go unnoticed" ([Cocoa with Love](https://www.cocoawithlove.com/2008/06/doing-things-in-cocoa-with.html)). **verified.**

## argument (117 words)

No system in the survey guards every pointer argument unconditionally, and the one that came closest walked it back: Ada 95 checked every access parameter at the call, Ada 2005 made access types nullable and moved the check to the dereference. Route D's premise is falsified by two release-shaped functions: `sqlite3_close(NULL)` is a harmless no-op, `fclose(NULL)` is undefined and segfaults in glibc. Route C's polarity is the one with a measured failure: Nim dropped default `not nil` before 1.0, C# 8 shipped annotations with no runtime check, and Apple had to invent region defaults because per-pointer opt-in never reached coverage. Kotlin's platform types, assert by default and believe the annotation when present, have shipped for a decade.

## condition

I change my reading on being shown either of these.

1. **For A over B**: a shipped system that guards every pointer argument outbound to C unconditionally, with no opt-out, and a program corpus that still binds `free`, `freeaddrinfo` or `sqlite3_close`. I searched ten systems and found none; one citation retires my objection.
2. **For C over B**: a measured annotation-coverage figure above roughly 80% for opt-in non-null annotations in a C header ecosystem after five years. Apple's region default, Nim's abandonment and C# 8's migration guidance all say the opposite, but the number would beat them.
3. **For D**: a published enumeration of C release functions showing NULL-accepting behaviour in a large majority, with `fclose`, `closedir` and `pthread_mutex_destroy` as the named exceptions. Then D becomes a default with an escape hatch rather than a guess.

## Prediction, and the command that scores it

**Prediction**: route F cannot replace route B's word, because the C headers of this Mac's SDK are mostly unannotated. Specifically, **fewer than 20% of `*.h` files under `$(xcrun --show-sdk-path)/usr/include` contain the token `_Nonnull` or `_Nullable`**, so a header-derived answer will be `CXTypeNullability_Unspecified` for the large majority of bindings and F must degrade to B's default.

```sh
S="$(xcrun --show-sdk-path)/usr/include"
A=$(find "$S" -name '*.h' | wc -l)
B=$(grep -rlE '_Nonnull|_Nullable' "$S" --include='*.h' | wc -l)
printf 'annotated %s of %s headers = %s%%\n' "$B" "$A" "$((100*B/A))"
```

Scored **held** if the percentage is under 20, **failed** at 20 or above. Not run in this seat: no shell. If it fails, F is promoted from a convenience to the primary source of the word, and B's `accepts_null` becomes the exception rather than the rule.

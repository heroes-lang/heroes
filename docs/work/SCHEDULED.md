# SCHEDULED — work that already has a milestone

Neither a question nor a decision: work with a **home**, waiting for it. Nothing
here needs the author, and nothing here should be done early — each item names
the milestone that will read it, and doing it sooner means doing it against a
smaller corpus, a smaller compiler, or a measurement not yet taken.

`/step` reads this when it opens the milestone named in the item — its § 1
Orient says so, and that line is the whole mechanism. **There is deliberately no
`/scheduled` skill**: a third verb reading a list `/step` already has to open
answers no question the other two do not, which is CLAUDE.md §10's stopping rule
applied to the skills instead of the CLI. A list nobody is *obliged* to open is
write-only, and the obligation is cheaper than a command.

**Only open items live here.** The moment one is done it is ticked with what
closed it and moved to `docs/work/DONE.md`. Eleven ticked items had accumulated
here by 2026-08-26, two of them ticked not because the work finished but because
the item had *moved elsewhere* — audit trail, which belongs in the record.

**EVERY ITEM'S FIRST FIELD NAMES A MILESTONE THAT HAS A ROW IN `docs/ROADMAP.md`
§ The chain AND IS NOT CLOSED** (author instruction 2026-09-04: *"fix SCHEDULED
too, so that every item is attached to a roadmap step that is still to be done;
if you cannot find one, create it"*). A milestone name, or a name plus a step —
never a waiting condition, never a description of a milestone, never a `grep`.
**If no open row does the work, one is created**: an existing row where a real
milestone genuinely does it, a new id placed by the author where none does, and
the id reaches a list before it reaches a row, which is CLAUDE.md §14's order and
what the `records/names` check reads.

**What the rule cost the day it was given**, measured over the **29** items then
open: **twelve had no home a reader could reach.** Nine named a waiting condition
instead of a milestone — *"the next panel that touches emission"*, *"trigger, not
a milestone"*, *"the milestone that makes the stack guard per-thread"* — and
three named a milestone that had **closed**, two of them M-corpus-depth, closed
that morning, and one M-ffi-ladder, closed 2026-08-12. That last one is the shape
worth remembering: it was filed the day before, out of a ratified sitting, at an
id that had been finished for three weeks. **A closed home and no home read
exactly alike in this list** — the item looks scheduled either way — which is why
the rule is about the first field and not about intentions. Four rows entered the
chain that day and this list stopped carrying row numbers at all: the order lives
in the chain table and nowhere else (§14), so a name here and a number there
cannot disagree.

**If an item loses its home it does NOT move to `docs/work/DECIDE.md`** — that
was this file's rule until 2026-09-04 and the instruction above replaces it. The
old rule said work scheduled at nothing is a decision nobody has made, and it
moved two items out on 2026-08-26, one named M-strings-ownership, closed
2026-08-05, and one naming no milestone at all. What it could not do is notice
the other twelve: an item only *moves* when somebody catches it, and nothing was
checking. A missing home is now answered by **giving it one**, with the author
placing any new id, and the audit trail stays in the item's own first field.

2026-09-02 | M-selfhost-nesting | The compiler's own hundred and seventy files were named like a filing cabinet nobody had bought — `check_state`, `emit_decls`, `resolve_walk` — and the job was to buy the cabinet: put them in folders and let the names get short. It is the most boring change imaginable, and it found three things. The first is that the long names had been doing a job nobody wrote down. Nobody ever calls a variable `emit_decls`; everybody calls one `decls`. The prefixes had been holding the module names apart from the ordinary words for values, silently, for free, and taking them off let the two collide in twenty-three places at once. The second is what the collisions were hiding. A file that borrows a module called `state` and also has a variable called `state` can write `state.value` twice and mean two different things, and the compiler said nothing at all: it printed seven on one line and a hundred and one on the next and exited happily. Both readings pass every check, because a piece of data that holds a number and a function that returns a number look identical from where you are standing. That program had been legal all afternoon and nobody had written it, because the long names made it unwriteable. And then the part that is either funny or frightening depending on the hour: the rule forbidding it had been decided four months earlier, in writing, by a panel, and approved — the very word *binds* in the language's one-page description was chosen for that purpose and the reason was recorded. The compiler simply never did it. Two of its own comments claimed it did. And a test, written on purpose, asserted the wrong behaviour was correct, so the contradiction between the ruling and the code sat in the repository with a green tick on it. The third thing turned up while looking for the second. This compiler offers to fix your program for you, and marks each repair either *certain* or *a guess*, and only applies the certain ones. One of them was wrong: given a variable wearing a module's name it would helpfully add the module's name in front — producing `window.window.destroy` — and then, asked again, `window.window.window.destroy`, forever. The project's own rules say that every automatic repair is checked to make sure the repaired program still compiles. It is. But the check can only read single-file examples, and every repair about modules needs two files to happen at all, so that whole family of repairs had never been checked once. Three rules, all written down, all correct, all cited in comments — and nothing in the building obliged to run any of them. The same evening turned up a fourth: one of the three test suites had been failing for six commits, over a number that a comment two lines above it promises will always be kept in step, and the command that would have shown it is listed in one document and in neither of the two that anybody follows.

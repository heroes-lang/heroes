2026-08-15 | **A C width stops being a constant: `long` and `unsigned long` are derived from the target, and `malloc` stops blaming the compiler** (author decision, `/decide`). `extern function malloc(size: i64) -> ptr` — the first thing anybody binds — exited **2** under *"internal error: compiling the generated C failed"* with raw clang output and a path under `build/<hash>/`, because `emit/ffi_narrowed.rs` mapped C types to Heroes widths through a **table** and `long`/`unsigned long` were deliberately absent: they are 64 bits on Darwin and Linux and 32 on Windows, so no tabled string is right on three legs. That correction was right about the table and wrong about the question — a missing row makes the class decline, and declining hands the failure to §7's exit-2 rule | the answer is that a width is not a constant, it is a question about the target: `word_width_bits()` reads `size_of::<c_ulong>()`, Rust's name for the same C type clang is about to compile, on the same machine for the same target, which is a fact about the value in hand rather than a premise about which platforms exist (CLAUDE.md §11).

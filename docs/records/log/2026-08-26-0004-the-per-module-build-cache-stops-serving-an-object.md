2026-08-26 | **The per-module build cache stops serving an object built against a header that has since changed** (M-separate-compilation step 7; acceptance row 2's second half, panel 093 R4; `selfhost/cli_deps.hero` new, `selfhost/cli_units.hero`, `selfhost/cli_toolchain.hero`, `selfhost/cli_verbs.hero`, `tests/harness/suite_cache.hero` new). **The defect was measured before the repair and it was a wrong answer at exit 0**: a two-module program whose `extern "conf.h"` group declares `constant CONF_LIMIT` printed `1` with the header on disk saying `2`, and then `1` again with it saying `7`. The cause is structural rather than an oversight — the accessor emits `return CONF_LIMIT;` whatever the header holds, so the emitted C is byte-identical across the edit and a key that contains the whole emitted C is blind to it **by construction**. §12's robustness rule puts this ahead of everything else in the file: a build system's worst outcome is a wrong answer that looks like a right one. **The mechanism is clang's own dependency listing** (`-MD -MT dep -MF`), riding the compile that is already happening: every TU records what it actually opened, transitively, with a content digest per file, and a warm object is served only when every one of them still hashes the same. Three alternatives were weighed and the numbers decided it — hashing the header names an `extern` writes down misses the file one level below and means re-implementing the include search; preprocessing first so the contents can enter the key literally costs a second clang pass per TU on 157 units; what landed gives R4's guarantee (a stale object is never reused) and gives up only directory retention, which costs a recompile and never an answer. **No sitting was convened**: this executes an acceptance row panel 093 already ruled, with no surface, no diagnostic class and no spec token — the choice of mechanism is recorded here so it can be overruled rather than discovered. **Three things fell out of the work and each is a measurement.** `runtime_text` was being asked once per translation unit — 157 shell `cat` invocations and 25 MB of hashing per build of the compiler (162 KB × 157, at this compiler's measured ~1.2 MB/s) for an answer that cannot change during a build; it is now a `Toolchain` field computed once at `locate_toolchain`. The record deliberately does **not** carry what lives under the key's own directory, asked of the path rather than assumed of its position: the first entry of every listing is the generated `.c`, ~90 KB per module, which would be 14 MB of hashing per build to re-answer a question the directory name already settled.

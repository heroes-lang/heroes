The binding declared it `@error`, passed a local, freed nothing — and never read the local either, because the message this program prints comes from `sqlite3_errmsg`. So it asked for an allocation it did not use. **Why the development machine could not see it**: LeakSanitizer does not exist on Darwin arm64 (CLAUDE.md §7), so `heroes test examples/ledger/main.hero --sanitize` was green here in all three configurations while leaking on every failure. **And no C warning can catch this class, measured rather than assumed**: the two forms written into one file and compiled with `clang -Wall -Wextra -Wunused-but-set-variable` produce **zero warnings on both**, because the slot is address-taken and clang counts taking an address as a use. That is what makes the class invisible below Heroes. **One hypothesis was raised and falsified before it was written down**: that `sqlite3_exec` clears the handle's error state after copying the message, so the program was reading it from the wrong place. Measured on both platforms — sqlite 3.51.0 here, 3.46.1 in the image — the out-parameter and `sqlite3_errmsg` answer the identical `no such table: nothing_at_all`, and neither clears anything. The FAIL was the leak detector making that test's process exit non-zero, which the repair confirmed by making both symptoms vanish with no assert touched.

  **The repair.** The fifth argument is declared a plain `ptr` and passed `nullptr`, which is what SQLite documents as *do not allocate one* — the resource is removed rather than a rule to free it added, so it cannot leak by construction on any SQLite version. **And the class was attacked, not the case** (CLAUDE.md §1: the provoking case is a witness). Three adjacent shapes were checked and two of them were live: `examples/sqlite/main.hero` carried the **identical** binding and leaked nothing only because no statement in it is ever refused, which is a fact about its SQL and not a defence — repaired the same way; and `opened()`'s failure path dropped the connection handle, which is much larger than 40 bytes. Measured on both platforms rather than read off the documentation: `sqlite3_open("/no-such-directory-here/x.db", &db)` answers **14** with `db` **non-NULL**, `sqlite3_errmsg` on that handle says `unable to open database file`, and `sqlite3_close` on it answers 0 — so the handle is released there now, and the failure carries SQLite's own reason instead of the sentence the program used to invent. Every other bound C function in the corpus that returns a pointer was checked and all five are library-owned (`sqlite3_errmsg`, `sqlite3_column_text`, `curl_version`, `curl_easy_strerror`, `SDL_GetRevision`), so they are read and never freed, which is correct; `curl_easy_init`'s handle reaches `curl_easy_cleanup` with no early return between them. **Verified**: 16 tests green at `-O0`, `-O2` and `--sanitize` on this Mac **and in the Linux container**, which is where it was red; the two blessed emission traces re-blessed after the diff was classified line by line — 8,350 differing lines in ledger's, of which 2,050 are `#line` into its own sources and 6,143 are `#line` restores into `main.c`, leaving **157** that are the repair itself, including the disappearance of `__attribute__((unused)) void * h2_error;` and of the invented message constant. **What it leaves open**: `heroes mutate` has no operator for this mistake, and the compiler has no rule against it — a local passed as `@` to an `extern` and never read afterwards is meaningless whatever C owns, the compiler already computes that fact in `selfhost/emit/body.hero:148`, and the shape exists at **four** sites in this corpus (the two `@error` repaired here and the two `@tail` of `sqlite3_prepare_v2`, harmless because that pointer is the SQL string's).

How to verify that it compiles itself

The Heroes compiler is written in Heroes. Compiling it requires nested data, name tables, recursion, error handling and programs spread across files. It is a practical test of how the language handles a complex program.

The repository, the project’s archive, also contains the compiler as one generated C file. You can build it on a computer without Heroes installed. Then use the resulting compiler to translate its own source into C and compare the two files: 

$ clang -I runtime seed/heroes.c runtime/runtime.c -o heroes
$ ./heroes build selfhost/main.hero --emit-c -o out.c
$ cmp out.c seed/heroes.c
                       (cmp prints nothing: not one byte differs)

  seed/heroes.c   the C the repository ships: the way in
  out.c           what the compiler writes when it compiles itself

  over 22 megabytes of C, and more than 700,000 lines of it

If the files are identical, cmp prints nothing. The comparison verifies that the compiler reproduces the C it was built from. The middle command takes under a minute on a MacBook Air. Anyone can repeat the test: the repository is open and the three commands are the whole of it.

Heroes implements every part of the compiler: reading the words and structure of the code, connecting names to declarations, checking types, creating and checking an intermediate representation of the program, managing memory, generating C, checking external libraries, reporting errors, formatting code and handling commands.

Errors found by compiling its own source

The new compiler initially rejected its own source, incorrectly reporting a structure that contained itself. Investigating this found defects in both the new compiler and its predecessor. One involved the underline in an error message: it covered the annotation that the test used to check its position.

Compiling the compiler’s source tests many language forms in one program. Several defects had the same cause: a loop jump inside a match branch skipped the instruction that updated a manually maintained index.

The final difference between the two files was the order of the lines. Some lists were already ordered in the previous compiler; the new one needed explicit sorting, as notes in the source had warned. Maps do not guarantee an order. Adding the missing sorts made the files identical.

How language changes are reviewed · five years ·

Changes to syntax, language rules, error messages or compiler structure are reviewed by a panel of five seats. Each seat receives different material, and four can veto a proposal. Internal compiler or runtime changes, which affect the code that supports execution, go to two of the five if they leave syntax, error messages and the specification unchanged.

  • The readerReceives the specification and sample programs, without the design document or compiler source. Tests whether the language can be understood. veto
  • The compiler engineerExamines the source and assesses how much code the change requires to write and maintain. veto
  • The C pragmatistCompiles the C code needed to use a library from Heroes, or documents why compilation fails. veto
  • The spec wardenCompares token counts before and after the change and checks that the specification stays within its limit. Tokens are the pieces of text a model reads. veto
  • The historianHas to search the web and cite dates and sources: unsourced precedent is inadmissible. It has also read the author’s history of programming languages, and uses it to know where to look rather than as the source, because a book by this project’s author cannot be evidence for this project. Advises without veto power.

The panel chooses the solution it considers strongest and most complete, then submits it to the author for approval. Work continues while confirmation is pending. If there is a more cautious alternative, it is recorded so the author can consider it.

Each review is recorded in a repository file, including the material examined, the verdicts and any vetoes. There are more than a hundred reviews. Every language change requires this review process.

Twenty lines

heroes this prints these principles, which are included in the compiler. They are reproduced here as the command prints them. 

The Zen of Heroes

 1. This language begins with a tribute to David Bowie.
 2. It is made for language models; people can read it too.
 3. A model may have read everything; each page must still explain itself.
 4. What the eye can see is all there is: sound and vision.
 5. There is one way to say each thing; every program sings in the same voice.
 6. That way may not be obvious at first; the Starman already knows it.
 7. The semantics are familiar; the syntax is new.
 8. Turn and face the strange: every strange choice here is deliberate.
 9. Nothing changes behind your back; every change signs its name.
10. Every plausible mistake must become a compile error before the program runs.
11. Unless you mark the unfinished place with ???.
12. An honest hole beats a confident guess.
13. A compile-time error is an answer; a runtime error is an ambush.
14. An error should tell you how to fix the program. Anything less is a complaint.
15. Repeating a word is cheap; forgetting one can cost the whole program.
16. The specification stays small under pressure; every word must earn its place.
17. Crashes and leaks are bugs. Ashes to ashes: what Heroes takes, it returns.
18. When pretty code and safe code disagree, safe code wins.
19. There is no standard library; C is the man who sold the world.
20. We can be heroes, just for one day.

Line 10 states the thesis, line 19 the initial constraint and line 18 the priority when two principles conflict. Why the language is built this way →

The continuous integration system, which runs automated checks, runs the first command on Linux when compiler changes are submitted. When a milestone version, a completed stage of the project, is tagged, it runs on three platforms. The other two commands run only on Linux: they check that the compiler reproduces its own C, which is the same across platforms. Decisions, reviews and measurements are in the repository, open to read.

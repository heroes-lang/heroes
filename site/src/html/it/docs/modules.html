I moduli e i file

Un file è un modulo, e il percorso che scrivi vuol dire la stessa cosa da qualunque punto.

Un programma più grande di un file deve rispondere a due domande, e molti linguaggi rispondono così male che poi la gente impara le risposte a forza di sbagliare. Dove va a cercare il compilatore un file? E come si chiamano le cose che ci sono dentro, una volta trovato?

Heroes risponde a entrambe in tre frasi. Un file è un modulo. use geom/point legge geom/point.hero partendo dalla cartella del file che compili. E il nome che quella riga ti dà è l’ultimo pezzo del percorso, quindi tutto quello che viene da quel modulo si scrive point.qualcosa.

Il percorso parte da dove sei partito tu

È la regola da tenere a mente, perché tutto il resto viene da lei. Lanci heroes run shapes/main.hero, quindi shapes/ è la radice, e ogni use di ogni file di quel programma si scrive a partire da lì.

Sei moduli in tre cartelle. Fin qui niente di strano. Vale la pena fermarsi sul file che sta due cartelle sotto e che raggiunge il modulo appoggiato lì accanto a lui:

area.hero e point.hero stanno nella stessa cartella, e area.hero scrive comunque il percorso intero. Un vicino non ha una scrittura più corta di un estraneo. Sembra un costo, finché non vedi cosa compra: la riga use geom/point è la stessa riga in main.hero, in geom/area.hero e in render/ascii.hero. Puoi copiarla, spostare il file che la contiene, leggerla al telefono a qualcuno che non ha l’albero delle cartelle davanti, e vuol dire sempre un file solo.

Non si può salire

Nessun .., nessuna barra iniziale, nessun modo di uscire dalla radice. Se ci provi, il compilatore ti dice qual è la regola invece di dirti solo che la sintassi è sbagliata: 

$ heroes check shapes/main.hero
error[module_path_climbs]: a `use` path cannot climb — every `use` starts at the directory of the file you compile, so write the path from there: `use lex/token`, wherever the file that writes it sits
  at shapes/geom/area.hero:8:5
    |
  8 | use ../geom/point
    |     ^
  note: a module above that directory belongs to a different program: give this one its own root, or move the file in

La nota in fondo è la metà interessante. Un file sopra la tua radice non è un file che ti sei dimenticato di raggiungere: fa parte di un altro programma, e tirarlo dentro vorrebbe dire che due programmi si dividono un modulo e nessuno dei due ne è il proprietario. Se ti serve, spostalo dentro oppure dai a tutto quanto una radice più larga. Sono entrambi un comando, e ti lasciano un albero di cartelle che qualcun altro riesce a leggere.

Il nome è l’ultimo pezzo

use geom/point lega point. Non geom_point, non geom.point: solo l’ultimo pezzo, così il punto in cui chiami resta corto e la cartella ne sta fuori.

Un nome che viene da un altro modulo si scrive sempre con il suo qualificatore davanti. Non c’è modo di staccare Point da point e usarlo nudo, e non c’è nessun asterisco che lo faccia per te. Così quando leggi point.span(...) sai due cose senza uscire dalla riga: viene da un altro file, e il blocco di use in cima a questo dice esattamente da quale.

Due moduli possono finire con la stessa parola

Siccome il qualificatore è solo l’ultimo pezzo, scale.hero nella radice e render/scale.hero vogliono chiamarsi entrambi scale. Niente impedisce che esistano tutti e due. Quello che viene rifiutato è un file che si prende quel nome due volte: 

$ heroes check shapes/main.hero
error[module_binding_taken]: this file already calls `render/scale` by the name `scale`, so `scale` cannot have it too — a file may not bind one name twice
  at shapes/main.hero:23:5
     |
  23 | use scale
     |     ^^^^^
  note: the two modules may both exist and both be used — `as` says what THIS file calls each one, and two files may name the same module differently

La riparazione sta sulla riga che il compilatore ti ha indicato, ed è una clausola sola:

use render/scale as near_scale dice come questo file chiama quel modulo. Un altro file dello stesso programma può chiamarlo scale e non nominare mai quello della radice. Il rinomino è locale, e questo è il punto: una collisione la puoi sempre risolvere nel file in cui capita, senza toccare un modulo che non hai scritto tu. Il programma stampa 10 per lo scale della radice e 3 per quello del vicino, quindi i due sono davvero due.

Il nome di un modulo è un nome

use geom/point mette point dentro il file come farebbe qualunque altra cosa, quindi nient’altro in quel file può prenderselo. Una variabile chiamata point lì accanto è lo stesso errore di ombreggiatura che ti ha già mostrato il capitolo 6: 

$ heroes check shapes/main.hero
error[shadowed_binding]: `point` is what this file calls the module `geom/point`, so a local may not take it — shadowing is an error here
  at shapes/main.hero:26:5
     |
  26 |     point = point.Point(x: 0, y: 0)
     |     ^^^^^
  note: rename the module for this file with `use geom/point as `, which clears every collision in it at once, or rename this binding

Senza quella regola, point.x in una funzione potrebbe voler dire il modulo e in un’altra funzione la variabile, nello stesso file, e le due cose compilerebbero entrambe. La nota offre le due riparazioni perché sono entrambe difendibili: rinominare il modulo sistema tutte le collisioni del file in un colpo, rinominare la variabile ne sistema una.

Cosa manca, di proposito

Nessun public e nessun private: tutto quello che un modulo dichiara è raggiungibile da qualunque file lo nomini. Nessun import con l’asterisco, quindi il qualificatore non è mai facoltativo. Nessun import circolare, e il compilatore lo rifiuta sulla riga use stessa invece che al momento del linker (il passo che cuce insieme i pezzi compilati). E nessun file di progetto, nessun manifest, nessuna configurazione: l’albero delle cartelle sul disco è tutta la disposizione, e il comando che scrivi è quello che decide la radice.

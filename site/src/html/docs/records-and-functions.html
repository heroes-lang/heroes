Records and functions

Data with a shape, and calls that cannot be read backwards.

A record is a named group of fields. It is the only way to give data a shape, there is nothing behind it, and it behaves like a number does: when you pass one to a function, the function gets a copy.

Point(3, 4) does not exist. Not “discouraged”: it is not a form the language has, so it is a compile error with the repair attached: 

$ heroes check points.hero
error[missing_label]: `Point`'s fields are always named — this one is `x`
  at points.hero:46:15
     |
  46 |     a = Point(0, 0)
     |               ^
  fix (certain): write `x: `

The cost is four characters at the call site. What it buys is that Point(y: 4, x: 3) and Point(x: 3, y: 4) are the same point and neither can quietly become the other. The few extra tokens sit exactly where a mistake is plausible.

Functions, and where the names become mandatory

A function’s first line is always written out in full: every value it takes has its type, and what it gives back is announced after the arrow ->. Inside, dx = … gives a name to a value once, and there is no type on it because the compiler can see it from the line. That working-out never leaves the function, though: the first line stays explicit, so you never have to read the body to learn what goes in and what comes out.

When two parameters of one function share a type, the call site must name them. dist2 takes two Points, so it does: 

$ heroes check points.hero
error[needs_label]: two of `dist2`'s parameters are `Point`, so every one of them is named at the call site — this one is `b`
  at points.hero:48:41
     |
  48 |     print("distance squared: ", a.dist2(b))
     |                                         ^
  fix (certain): write `b: `

Two arguments of the same type in the wrong order is the mistake no type checker can see, because both orders type-check. It is also the mistake a model on autopilot makes most often. The rule spends tokens in exactly that spot and nowhere else: where the types already differ, the compiler can tell the arguments apart and no label is required.

A call can be written from either end

x.f(y) means f(x, y), and the rule ends there. It is just another way of writing the same call: there are no methods, meaning no functions attached to a type, and nothing is looked up while the program runs.

So unit.translate(p).area() and area(translate(unit, p)) are the same call, and you write whichever one reads better where you are standing. Chains stay left to right without anyone having to define a class.

Tests live next to what they test

test is a top-level declaration like any other, and an ordinary build ignores it. The second test says that moving a rectangle does not resize it. That is a property rather than a number, and it reads as one sentence because of the call syntax above. 

$ heroes test examples/gallery/01-points.hero
ok   "the 3-4-5 triangle"
ok   "a rectangle keeps its size when it moves"
2 tests, all passed

What is deliberately missing

No inheritance, no interfaces, no overloading, no default parameter values, no variadic functions of your own. Every one of those makes the question which code does this call actually run require reading a second file, and answering that question in one place is the point of the language.

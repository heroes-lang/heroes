Records and functions

Grouping data in records and calling functions with explicit arguments.

A record groups fields with names and types. When you pass it to a function, the function receives an independent copy, as it does with a number.

Point(3, 4) is invalid because the field names are missing. The compiler reports the error and suggests a fix: 

$ heroes check points.hero
error[missing_label]: `Point`'s fields are always named — this one is `x`
  at points.hero:46:15
     |
  46 |     a = Point(0, 0)
     |               ^
  fix (certain): write `x: `

With field names, Point(y: 4, x: 3) and Point(x: 3, y: 4) describe the same point. Argument order does not change which value is assigned to each field.

Functions, and where the names become mandatory

A function declaration specifies the type of every parameter and, after ->, the result type. Inside the body, dx = … gives a value a name and the compiler infers its type. You can therefore find the input and output types by reading the declaration.

When two parameters of a function share a type, the call must name them. This applies to dist2, which takes two Point values: 

$ heroes check points.hero
error[needs_label]: two of `dist2`'s parameters are `Point`, so every one of them is named at the call site — this one is `b`
  at points.hero:48:41
     |
  48 |     print("distance squared: ", a.dist2(b))
     |                                         ^
  fix (certain): write `b: `

A type alone cannot distinguish two arguments of that type. Names make each argument’s role explicit. If the types differ, the compiler can distinguish them and labels are optional.

Calls with dot syntax

x.f(y) means f(x, y). Dot syntax is another way to write an ordinary function call. It does not define a method, a function attached to a type; the compiler determines which function to call before execution.

unit.translate(p).area() and area(translate(unit, p)) perform the same calls. Choose the form that reads best; dot syntax lets you read the operations from left to right.

Tests live next to what they test

A test block is declared outside functions, beside the code it checks. Ordinary builds ignore it. Here the second test checks that moving a rectangle does not change its area. 

$ heroes test examples/gallery/01-points.hero
ok   "the 3-4-5 triangle"
ok   "a rectangle keeps its size when it moves"
2 tests, all passed

Function limits

Heroes has no inheritance, interfaces, overloading, meaning multiple functions with the same name, or default parameter values. You cannot define functions with a variable number of arguments. These limits reduce the rules needed to understand a call.

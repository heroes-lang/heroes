Modules and files

One file is one module, and the path you write means the same thing from everywhere.

A program bigger than one file has to answer two questions, and most languages answer them badly enough that people learn the answers by accident. Where does the compiler look for a file? And what do you call the things inside it once you have found them?

Heroes answers both in three sentences. One file is one module. use geom/point reads geom/point.hero, starting from the directory of the file you compile. And the name that line gives you is the path’s last part, so everything from that module reads point.something.

The path starts where you started

This is the one rule to hold on to, because everything else follows from it. You run heroes run shapes/main.hero, so shapes/ is the root, and every use in every file of that program is written from there.

Six modules in three directories. Nothing there is surprising yet. Stop on the file one directory down, which reaches the module sitting right next to it:

area.hero and point.hero are in the same directory, and area.hero still writes the whole path. A neighbour gets no shorter spelling than a stranger. That looks like a cost until you notice what it buys: the line use geom/point is the same line in main.hero, in geom/area.hero and in render/ascii.hero. You can copy it, move the file that holds it, and read it out loud to somebody who does not have the tree in front of them, and it still means one file.

There is no way up

No .., no leading slash, no way to leave the root. Try it and the compiler tells you what the rule is rather than what the syntax was: 

$ heroes check shapes/main.hero
error[module_path_climbs]: a `use` path cannot climb — every `use` starts at the directory of the file you compile, so write the path from there: `use lex/token`, wherever the file that writes it sits
  at shapes/geom/area.hero:8:5
    |
  8 | use ../geom/point
    |     ^
  note: a module above that directory belongs to a different program: give this one its own root, or move the file in

The note is the interesting half. A file above your root is not a file you forgot to reach: it is part of some other program, and pulling it in would mean two programs share a module and neither owns it. If you want it, move it in or give the whole thing a bigger root. Both of those are one command, and both leave you with a tree somebody else can read.

The name is the last part

use geom/point binds point. Not geom_point, not geom.point: just the last part, so the call site stays short and the directory stays out of it.

A name from another module is always written with its qualifier. There is no way to pull Point loose from point and use it bare, and no wildcard that does it for you. So when you read point.span(...) you know two things without leaving the line: it comes from somewhere else, and the use block at the top of this file says exactly where.

Two modules can end in the same word

Because the qualifier is only the last part, scale.hero at the root and render/scale.hero both want to be called scale. Nothing stops them existing. What is refused is one file claiming the name twice: 

$ heroes check shapes/main.hero
error[module_binding_taken]: this file already calls `render/scale` by the name `scale`, so `scale` cannot have it too — a file may not bind one name twice
  at shapes/main.hero:23:5
     |
  23 | use scale
     |     ^^^^^
  note: the two modules may both exist and both be used — `as` says what THIS file calls each one, and two files may name the same module differently

The repair is the as clause on line 22 of the file above, and with it both names are usable:

use render/scale as near_scale says what this file calls that module. Another file in the same program can call it scale and never mention the root’s. The rename is local, which is the whole point: you can always fix a collision in the file where it happens, without touching a module you did not write. The program prints 10 for the root’s scale and 3 for the neighbour’s, so the two really are two.

A module’s name is a name

use geom/point introduces point into the file the way anything else does, so nothing else in that file may take it. A variable called point beside it is the same shadowing error chapter 6 already showed you: 

$ heroes check shapes/main.hero
error[shadowed_binding]: `point` is what this file calls the module `geom/point`, so a local may not take it — shadowing is an error here
  at shapes/main.hero:26:5
     |
  26 |     point = point.Point(x: 0, y: 0)
     |     ^^^^^
  note: rename the module for this file with `use geom/point as `, which clears every collision in it at once, or rename this binding

Without that rule, point.x in one function could mean the module and in another function the variable, in the same file, and both would compile. The note offers both repairs because either is defensible: renaming the module fixes every collision in the file at once, renaming the variable fixes one.

What this leaves out on purpose

No public and no private: everything a module declares is reachable from any file that names it. No wildcard import, so a qualifier is never optional. No circular imports, which the compiler refuses on the use line itself rather than at link time. And no project file, no manifest, no configuration: the tree on disk is the whole of the layout, and the command you type is what fixes the root.

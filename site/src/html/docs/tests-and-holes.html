Tests and holes

Tests you do not install, and a way to ask the compiler what goes here.

A test lives in the file it tests. A ??? asks the compiler what belongs in a place you have not written yet. Neither is installed: both are part of the language.

test is a declaration

A test has a sentence for a name and whatever is indented below it for a body. It sits next to the code it is about, in the same file, and an ordinary build ignores it entirely: nothing about tests reaches the executable you ship. There is no library to choose for writing them, nothing to mark them with, no separate directory, and no file names to obey.

assert takes a bool. When one fails it shows the expression it was given and both sides of the comparison, so you almost never have to add a print and run it again: 

$ heroes test points.hero
assert failed: dist2(a: Point(x: 0, y: 0), b: Point(x: 3, y: 4)) == 24
  left:  25
  right: 24
FAIL "the 3-4-5 triangle"
ok   "a rectangle keeps its size when it moves"
2 tests, 1 failed

The other tests still run and still report. The exit status is non-zero, so this works in a script without anyone parsing the output.

??? is a legal expression

Now the other half. Write ??? anywhere a value belongs and the program still type-checks: everything around the hole is verified as usual, and the compiler tells you what belongs in it.

Ask the compiler about that file and it answers:

$ heroes check holes.hero
hole at holes.hero:24:5
  position: statement — any type, or none
  this function returns: Entry
  in scope:
    entries: [Entry]
hole at holes.hero:28:74
  expected type: str
  in scope:
    entries: [Entry]
  functions that return it:
    summary_of(entries: [Entry])
      # The hole can be one argument of an otherwise finished line.

Read the second one. The compiler worked out that a str belongs there. Then it listed what you have to hand at that point, and which functions return a str, each with the first line of its comment: that is the documentation. It is the answer to “what could go here?”, which is the question you actually have, not an error message dressed up as help.

Everything else still gets checked

A file with holes is checked completely: exit 0, and diagnostics for anything genuinely wrong. What it does not do is produce a binary, and the tool says which line stopped it: 

$ heroes test holes.hero
no binary: 2 holes in holes.hero
hole at holes.hero:24:5
  position: statement — any type, or none
  this function returns: Entry
  in scope:
    entries: [Entry]
hole at holes.hero:28:74
  expected type: str
  in scope:
    entries: [Entry]
  functions that return it:
    summary_of(entries: [Entry])
      # The hole can be one argument of an otherwise finished line.

The compiler can therefore check a half-written program without mistaking it for a finished one. A hole cannot reach an executable.

Why this is in the language rather than in an editor

The reader of a Heroes program is often a language model, and a model writing code has exactly this problem: it needs to know what is available at a point in a file it has not finished. Written as a hole, that question is asked with three characters and answered by the compiler in a form both a person and a model can read, without an editor, an extension, or a running language server. The same three characters mark the place in the file, so nobody forgets there was a question.

Fill both holes and that main runs. Until then, the finished part of the file has a test that passes and the unfinished part has a question with an answer.

Maps

A lookup hands you a value or an error, and never a surprise.

A map is written {K: V} and holds values under keys. The interesting part is what happens when you ask for a key that is not there. In most languages that is where null gets in, or an exception, or a silently invented zero. Here it is a type.

m[k] is a V?, not a V

Write the lookup on its own and the compiler tells you what you actually have: 

$ heroes check maps.hero
error[type_mismatch]: expected `i64`, found `i64?`
  at maps.hero:9:12
    |
  9 |     return scores[name]
    |            ^^^^^^^^^^^^
  fix (guess): `.must()` — abort on the error case, giving `i64`

i64? is the fallible type from chapter 4: a number, or an error saying why there isn’t one. For a missing key that error always has the code missing_key. So the question what if it is not there is not a thing you might forget to ask: it is in the type of the thing you are holding, and you cannot use the number until you have answered it.

Four answers, one line each

.default(v): the value, or this one if the key is missing. The result is a plain i64, because the question has been answered.

.is_err(): asking whether the key is there, without taking the value out. This is the “does it contain” test, and it is the same call you would use on any fallible value.

.must(): take the value, and stop the program if there isn’t one. It is safe here because the line above has just checked, and that is the shape to use it in: .must() after a proof, never as a way to get past the type.

match: the general one, and the only one that puts the error itself in your hands. Both arms are required, as always, so neither case can go unanswered.

Building one

Writing it out all at once is one way in. The other is to declare a modifiable map with @ and write into it one key at a time: m[k] @ v puts the value in place of whatever was there. A map that starts empty has to be told its type, like every empty container: m: {str: i64} @ {}.

A map has no order, and the language means it

keys(m) gives you the keys in no particular order, and that is not a hedge in the documentation: two runs may differ. When the order matters, ask for it:

That is a real test from a bigger example, walking every room and every exit in a fixed order so the test says the same thing every time it runs. The same rule caught out this project’s own compiler: three lists that came out in map order made two builds of the same program differ, and the fix was three sort calls somebody had written a note about long before. The story is on the self-hosting page. Comparison, on the other hand, ignores order entirely: two maps with the same pairs are == however they were built.

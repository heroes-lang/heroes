Heroes / Docs / chapter 13

Packages

Code somebody else published, copied into your program and checked at every build.

The modules of chapter 12 are files of your own program. A package is code others publish: a tree of modules with a version, which your program fetches into its own folder and carries from then on. On this page each word means one thing: a module is one .hero file, a package is code a program fetches, and a library is C code a build links, the subject of chapter 15. The author asked for one name for one thing, and a sitting of the design panel, the judges every change to the language goes before, settled the three.

Heroes imposes no standard library. The language gives a program its built-ins and nothing more, and what a program needs beyond them it takes from a C library or from a package. This project writes one package of that kind, Rebel, a broad library in Heroes for text, files, numbers, the network and the common data formats: a program takes it or leaves it, and the compiler itself is written without it. This chapter uses Rebel to show how any package is taken.

Fetching a package

Rebel publishes all its packages together under one name, rebel, and a program names each one it uses. This small program reads a table written as CSV, comma-separated values, the plain text a spreadsheet saves, with Rebel’s csv:

Check it before it has fetched anything, and the line that names the package says what is missing: 

$ heroes check --brief reach_csv.hero
reach_csv.hero:5:5: error[unknown_entry]: `<rebel>` names no entry: there is no catalogue `heroes.toml` beside `reach_csv.hero`, the file you compile, and a package's module is read only through its entry there — `heroes add rebel` writes one

The command that fetches is heroes add, run in the program’s folder. A package is read from an index, a place that lists every version of every package it holds. The Heroes index on the web is not built yet, and no index publishes Rebel today: a program of yours takes it from a clone of this repository, by the path of its folder, the third source further down. What follows is how a package is taken once an index publishes it: here a small index made for the purpose, a folder beside the program, publishes Rebel’s version 0.1.0, and the command names it. The first command takes the entry; the second names the one package of it this program uses: 

$ heroes add rebel --index file://../index
added rebel 0.1.0
wrote heroes.toml
$ heroes add rebel/csv
added rebel/csv
placed rebel 0.1.0 heroes.packages/rebel@0.1.0-d15253004def87ef, 58 of 1637 files: what its `packages` line names and the modules those use
wrote heroes.toml

And the program builds and runs: 

$ heroes run reach_csv.hero
Low
Heroes

heroes add did two things. It wrote a file beside reach_csv.hero, the catalogue, and it placed a copy of the package’s files inside the program’s folder: not the whole of Rebel, more than sixteen hundred files and more than thirty megabytes, but csv and the modules csv itself uses, a few dozen files and under a megabyte. From then on the program needs neither the index nor the network: heroes build, heroes check and heroes run never fetch anything. Only heroes add and heroes fetch reach out, and a package that is missing, or does not match, is an error that names heroes fetch. The sitting that designed the package manager made that a rule: the compiler may use the network only where the answer was written down in advance, and for a package that answer is its fingerprint, further down. Go, the language whose package system this one copies, was measured fetching during a build; a Heroes build never does.

A program that uses no package has no catalogue. Every program in the chapters before this one builds as it always did, with no file beside it: the design was measured from the start on the files a program must have, and the answer for a program that depends on nothing is none.

The catalogue, line by line

$ cat heroes.toml
index = "file://../index"

[dependencies.rebel]
version = "0.1.0"
sum = "sha256-18a28f4305b947efe25e21d813d55f48c2caa8b223ebb0a21b16aff2e88c1d64"
packages = ["csv"]

index is the address the two commands read packages from. [dependencies.rebel] opens the entry, and rebel is the name the code writes between angle brackets. version is exact: no range, no “this one or newer”. sum is the package’s fingerprint, a number computed from every byte of its files, and the build refuses a copy whose bytes give another. packages lists the packages of the entry the program uses, each written as the path that follows the brackets: an entry that publishes many packages under one version, as Rebel does, places only those, with every module they use. An entry with no packages line places its whole version.

Nobody types the catalogue: heroes add writes it, and heroes add rebel/json adds a name to the line. The sum is sixty-four digits and letters after its sha256-, which nobody can write from memory, so an entry written by hand, by a person or by a model, has no sum to put in it, and the sitting had the specification name the command for that reason.

A use that names a package the line leaves out is refused where it stands, with the command that adds it: 

$ heroes check reach_csv.hero
error[package_not_listed]: `<rebel>/json` is not among the packages the entry `rebel` places, the ones its `packages` line names
  at reach_csv.hero:6:5
    |
  6 | use <rebel>/json
    |     ^^^^^^^^^^^^
  note: `heroes.toml`'s `[dependencies.rebel]` places `csv`, with the modules each one uses; `heroes add rebel/json` adds `json` to its `packages` line, and a program names every package it uses there

So the catalogue says, to anybody who opens it, every package the program uses, and a program that reads CSV does not carry Rebel’s web server, its cryptography and its time zones. A later sitting added the line, and ruled that it binds a path entry too, the third source further down.

The format is TOML, a small format for files of settings that Rust’s Cargo and Python’s pyproject.toml use too, read here as a strict subset. Every value is a string between double quotes, or a list of them, so version = 0.1.0 written bare is refused at its line and never read as a number. The file is read whole or not at all: a mistake on any line names no package, the lines above it included. And reading it runs no code. The sitting is plain about what it did not show: in its test with language models every format did equally well, because the models copied the example they were given. TOML was chosen for its comments, its named keys, its strictness and its being familiar from Cargo, and not because models write it better.

Mine and fetched: the angle brackets

Two kinds of use can stand side by side in one file. use book/entry, without brackets, is a module of the program, read from its root as in chapter 12. use <rebel>/csv is the module csv of the package the catalogue calls rebel. The brackets are the whole difference between mine and fetched, and you see it on the line without opening another file. That was the author’s call, made before the panel sat; the sitting tested it rather than ruled on it, and the two other spellings it tried beside it did no better.

Between the brackets goes a name, never an address. In Go an import carries the address of the repository it comes from; here the address lives in the catalogue, and the code says only rebel. When a package moves, from a git repository to an index for instance (git is the tool most projects keep their history in), the catalogue’s entry changes and no line of code does. Write an address anyway and the compiler says where it belongs: 

$ heroes check reach_csv.hero
error[use_holds_an_address]: `git.example.org/ana/rebel` is an address, which the catalogue `heroes.toml` beside the file you compile holds and a `use` never does: the `use` names its entry between `<` `>`, then a module of the package — `use <rebel>/csv`, `rebel` standing for the entry the catalogue gives that address
  at reach_csv.hero:5:5
    |
  5 | use <git.example.org/ana/rebel>/csv
    |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^
  fix (guess): write `<rebel>`

The two kinds never stand in for each other. A use with brackets is read only through the catalogue, and one without only from the program’s own folders, with no fallback either way. So deleting the catalogue, deleting an entry or mistyping one of its fields never changes which module compiles, only whether the program builds. The design document admits the catalogue on that condition and no other, with one exception, a path entry, which this chapter comes back to.

heroes fmt keeps the two kinds apart on the page as well: packages first, then the program’s own modules, a blank line between, each group sorted by its path. The compiler walks the modules in that same order, so the order you write them in changes nothing it does, only the line numbers of the file.

Where the copy lives

$ ls heroes.packages
rebel@0.1.0-d15253004def87ef

heroes add placed the package in a folder of the program called heroes.packages/, under a name made of the entry, its version and sixteen hexadecimal digits (the digits 0 to 9 and the letters a to f) computed from the entry’s fields and the index line. A mistyped field therefore names a folder that is not there, and the build says so. Inside is a byte-for-byte copy of the files the packages line reaches, as the index publishes them, and one file more, heroes.list, the version’s own list of files, which the fingerprint further down is computed from. The program keeps that folder in its repository beside its own files.

No use can spell the folder, because a part of a use path cannot hold a dot. Try, and the compiler answers that this is the folder a fetch placed a package in, “which a use never names”. So the copy is reached only through its entry, and with the entry gone the copy compiles nothing: every use <rebel>/… is refused, the folder still there.

Why inside the program, and not in a cache, a folder every program on the machine shares, as Go keeps one? The sitting’s compiler engineer gave the reasons. Every name the compiler prints of a fetched module is relative to the program and the same on every machine, in its messages and in the line markers of the C it writes, where a debugger, the tool that stops a running program to look inside it, finds the file names. No user’s cache folder is read, so no rule about where each system keeps one enters the compiler. And two programs never share a copy, so two builds never wait for each other. What it costs is a copy per program, and a folder that anything can edit: an editor, a script, a slip of the hand. The second cost is what the fingerprint, checked at every build, is for.

Inside a package, a use starts at its own root

$ grep '^use ' heroes.packages/rebel@0.1.0-d15253004def87ef/csv.hero
use csv/internal/scan
use csv/internal/stream
use csv/internal/write
use io

These are the use lines of Rebel’s csv.hero. Its use csv/internal/scan does not start at your program’s root, where there is no csv/ folder, and its use io does not mean a module of yours called io: inside a package, a use starts at the package’s own root, and a use with brackets names an entry of the package’s own catalogue.

The reason is the folder’s name above. The package’s author cannot know it: it holds digits computed from the entry, so it changes with the version and with the index line. The same Rebel 0.1.0, added to a program that reads the index by another path, landed in rebel@0.1.0-49a40d649ebcc399. A use written from the program’s root would have to name that folder; written from the package’s own root it is the same in every program, so a package moves from one program, index or version to the next without one of its use lines changing.

Private modules: internal/

The module csv/internal/scan reads the rows out of a text for csv, and no program calls it. A module under a folder called internal belongs to the module before the last internal in its path, here csv, and only that module and the modules under it may name it. From a program whose entry places the whole of Rebel: 

$ heroes check reach_csv.hero
error[private_module]: `<rebel>/csv/internal/scan` is private to `<rebel>/csv`: a module whose path holds `internal` as a part after its first, a folder's name or its own, is named only by the module the path before the last such part names and by the modules under it; name what `<rebel>/csv` offers instead
  at reach_csv.hero:5:5
    |
  5 | use <rebel>/csv/internal/scan
    |     ^^^^^^^^^^^^^^^^^^^^^^^^^

The rule is Go’s, which has had it since Go 1.4, and here it binds your own folders too: in a program with geom/shapes.hero and geom/internal/sq.hero, geom/shapes may write use geom/internal/sq and main.hero may not.

What it buys is a package whose face, the module a program names, is the whole of what a program can depend on. Each face’s reference, which heroes doc prints from the face and its comments alone, is the whole of what a program needs to read, and Rebel’s page links the reference of every one. The modules under internal/ are free to change between versions, since no program can have named them.

The fingerprint

Each version an index publishes has a list: one line per file, the file’s SHA-256 and its name, sorted by name. SHA-256 is a standard recipe that turns any bytes into sixty-four hexadecimal digits, and into entirely different ones if a single byte changes. The lines of Rebel 0.1.0’s list for csv: 

$ grep ' csv' index/rebel/0.1.0/list
e64377075e9641347e9d5b839d69dadec9fcd6555ceb3989be04b3253287d70f  csv.hero
a71db5362ebf16884fc793ddc8808f68071f212f98e69baf8f0663ceef389869  csv.ledger
94c41f1371df46b9fff460935907758db452953456518b85d15c4310cf0aaab8  csv/internal/scan.hero
0c4dea86875d2a93519e266d5f10be3de758ab94b5f50759ed9c0cdd7f1f71e7  csv/internal/stream.hero
2de58918bd811375b370249c397bca59618ad79c8de1461da6a6db04765286f0  csv/internal/write.hero

The SHA-256 of the list is the version’s fingerprint. The index keeps one line per version in a file called versions, and the catalogue’s sum repeats the line of the version it holds. Anybody can check those digits with nothing of Heroes: 

$ cat index/rebel/versions
0.1.0 sha256-18a28f4305b947efe25e21d813d55f48c2caa8b223ebb0a21b16aff2e88c1d64
$ shasum -a 256 index/rebel/0.1.0/list
18a28f4305b947efe25e21d813d55f48c2caa8b223ebb0a21b16aff2e88c1d64  index/rebel/0.1.0/list

A copy placed by a packages line holds part of the version, so it keeps that list beside its files, heroes.list, and is held to the sum through it: every file it holds must be a line of the list as it stands, and the list must give the sum. A file the line left out is no change; a byte changed, a file added or the list edited is one. The compiler checks the copy in heroes.packages/ against the sum at every build, every check and every run. Change one byte of it, here a d made a t in csv.hero, and the build stops before it compiles anything: 

$ heroes build reach_csv.hero
error[package_unread]: `<rebel>` cannot be read: the tree placed at `heroes.packages/rebel@0.1.0-d15253004def87ef/` is `sha256-7fe79c89bcd7d17c5d83e00c9dc86664a4a0b53b15390f3413b6eb077d4e7889`, and the catalogue's `sum` for it is `sha256-18a28f4305b947efe25e21d813d55f48c2caa8b223ebb0a21b16aff2e88c1d64`: a file of it, or the listing `heroes.list` it keeps, was changed since it was placed — move it out of `heroes.packages/` to keep the change, or remove it, and `heroes fetch` places it again
  at reach_csv.hero:5:5
    |
  5 | use <rebel>/csv
    |     ^^^^^^^^^^^

heroes fetch never writes over the change, because an edit may be the author’s own work: it stops, names the file that changed and says what to do, which is to move the folder out of heroes.packages/ to keep the change, or to remove it to have the published tree placed again: 

$ heroes fetch
heroes.toml:5: error[sum_mismatch]: `rebel` 0.1.0 from the index `file://../index` is placed at `heroes.packages/rebel@0.1.0-d15253004def87ef`, and that tree was changed since it was placed: `csv.hero` changed; the change is yours, so nothing was placed over it: move the folder out of `heroes.packages/` to keep the change, or remove it to have the tree placed again

Removed, the tree comes back from the index, which is held to the same standard on the way: each file heroes fetch copies must match its line of the list and the list must match the catalogue’s sum, or nothing is placed. 

$ rm -r heroes.packages/rebel@0.1.0-d15253004def87ef
$ heroes fetch
placed rebel 0.1.0 heroes.packages/rebel@0.1.0-d15253004def87ef, 58 of 1637 files: what its `packages` line names and the modules those use

Why at every build, and not only when fetching: the copy lives in a folder anything can edit, and an edited copy compiled without a word is the silent failure this language exists to refuse. The check is the SHA-256 of the runtime, the piece of program that sits underneath every Heroes program, written in C, and never a package’s code: in the words of a later sitting, the verifier stays out of the verified, so no package can vouch for itself. Every file counts, .hero or not, because a C header a package carries, the file that tells the compiler how a C library is shaped, is code the program trusts too.

A published version never changes

A version, once published, is never edited: a change to a package is a new version. crates.io, Rust’s index, says it of every crate it holds, and goes one step further: “The version can never be overwritten, and the code cannot be deleted.” Here the fingerprint holds the first half: a file of a version changed after a program took it no longer matches its line of the list, and heroes fetch refuses to place it, saying which file.

The second half, code that is never deleted, is one no index here promises yet: until a package reaches 1.0.0 an index may drop its older versions. That breaks no program that still holds one: its copy stands in its own folder, held to its own sum, and it builds and runs as before. A program keeps the version it fetched until it asks for another, and the command that moves it to the newest is the one that took the package. Here the small index has since published a version 0.1.1: 

$ heroes fetch
kept rebel 0.1.0 heroes.packages/rebel@0.1.0-d15253004def87ef, 58 of 1637 files: what its `packages` line names and the modules those use
$ heroes add rebel
changed rebel 0.1.0 -> 0.1.1
wrote heroes.toml
removed rebel 0.1.0 heroes.packages/rebel@0.1.0-d15253004def87ef, which no entry names now

The same command took away the copy of 0.1.0, which no line of the catalogue names any more, and said so. A copy that holds a change of yours is never taken away: it stays where it is, and the command says that too.

So a change to a package never breaks a program’s build: it reaches a program only when the program asks for it.

One version of each package

A program holds one version of each package, and its catalogue lists every package the build compiles, the packages its packages need included. When two of them need two versions of a third, heroes add keeps the higher one: that is Go’s rule, called minimal version selection. Here a small index made for the purpose holds a, which needs strs 1.0.0, and b, which needs strs 1.1.0: 

$ heroes add a --index file://../index3
added a 1.0.0
added strs 1.0.0 for a
wrote heroes.toml
$ heroes add b
added b 1.0.0
changed strs 1.0.0 -> 1.1.0 for b
wrote heroes.toml
$ heroes run main.hero
a sees 1.1.0
b sees 1.1.0

The choice is made once, by the command, and written down; the compiler solves nothing, and a catalogue that leaves out one of those packages is refused, never completed. Since the catalogue holds the whole list with every sum, nothing else stands beside it: no lock file, the second file other systems keep to pin what was chosen. Russ Cox, who designed Go’s rule, wrote that it “leads to reproducible builds without lock files”.

Why one version: a package compiled twice is two packages. Its records become two types with one name, and a value one copy hands out is refused where the other’s is expected. Reach one folder both as a package and as a module of your own, which only a path entry allows, and that is what happens: 

$ heroes check main.hero
note: the package `lib` is read from the folder `lib/`, a `path` entry of the catalogue: unverified, no fingerprint holds it
error[type_mismatch]: expected `counter.Box`, found `own.Box`
  at main.hero:7:22
    |
  7 |     b: counter.Box = own.boxed(3)
    |                      ^^^^^^^^^^^^

Dart records the same failure: one file reached by two spellings, which Dart’s own guide says it takes for “two completely unrelated libraries”.

Two other sources: git, and a folder of your own

An entry can name a git repository instead of an index. A commit is one saved state of a repository, and a tag a name given to one commit, such as v0.1.0. heroes add with an address and --tag writes the address, the tag, the commit the tag names and the sum. The repository here is a local one made for the purpose: 

$ heroes add file://../greet --tag v0.1.0
added greet v0.1.0
wrote heroes.toml
$ cat heroes.toml
[dependencies.greet]
git = "file://../greet"
tag = "v0.1.0"
commit = "e191abf1ce560fd3020d201ed56e76d43dcb1eb6"
sum = "sha256-09cac94c6a5803de196d94dc80c9da89329c20ce2ee673a876de3a4d5ac381d3"

The commit is there because a tag can be moved to another commit. A moved tag is refused, never followed: 

$ heroes fetch
heroes.toml:3: error[tag_moved]: the tag `v0.1.0` of `file://../greet` names the commit 07290184ea57bf707fa8c8e2b30e3a278ebc80fa, and the entry `greet` was written when it named e191abf1ce560fd3020d201ed56e76d43dcb1eb6: a tag that moved is refused, never followed, and `heroes add` writes the entry again once the new commit is the one meant

On the network an address is https://: a plain http:// is refused, being “read in clear, so anything between could change what is fetched”. And file:// is accepted only for a folder inside the program’s own repository, which is how the transcripts on this page read their small indexes.

The third source is a folder of your own, heroes add --path, for a package you are still writing, or for a package you have as a folder, as a clone of this repository holds Rebel (here the clone, heroes, stands beside the program’s folder). It is read where it stands and never copied, and nothing holds it to a fingerprint, so every build says so. A packages line binds it as it binds any entry: 

$ heroes add --path ../heroes/rebel/library/0.1.0/files --as rebel
added rebel ../heroes/rebel/library/0.1.0/files
wrote heroes.toml
$ heroes add rebel/csv
added rebel/csv
wrote heroes.toml
$ heroes check reach_csv.hero
note: the package `rebel` is read from the folder `../heroes/rebel/library/0.1.0/files/`, a `path` entry of the catalogue: unverified, no fingerprint holds it

It is the one exception to the promise that a catalogue’s mistake never changes which module compiles: a path pointing at the wrong folder compiles other code. The author listed a local folder among the sources, so the sitting kept it, and made it loud rather than silent.

What exists today

One package of this project’s own, Rebel, in the folder rebel/library/ of the repository, the folder that holds all its files and their history, with more than a hundred packages a program can name, every one written in Heroes. What Rebel needs of the operating system it reaches through C: the runtime’s own, the C this project writes and ships beside the runtime, which a program carries only where it calls it, and for a few packages a library of the system, as sql/sqlite stands on SQLite’s. The programs that use it, each package’s own test program among them, are the folder rebel/examples/, and they read Rebel through a path entry.

A catalogue with no index line reads the Heroes index, a site that is not built yet: building it, publishing a package to it and deciding who may take a name make a milestone of its own, M-package-index, on the roadmap. Until it exists, a package from outside this repository comes from git, or from a folder of your own. The rules every package of Rebel follows, for whoever writes the next one, are Rebel’s guide for its writers.

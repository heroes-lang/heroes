Heroes / Guide / chapter 13

Packages

Code somebody else published, copied into your program and checked at every build.

The modules of chapter 12 are files of your own program. A package is code others publish: a tree of modules with a version, which your program fetches into its own folder and carries from then on. On this page each word means one thing: a module is one .hero file, a package is code a program fetches, and a library is C code a build links, the subject of chapter 15. The author asked for one name for one thing, and a sitting of the design panel, the judges every change to the language goes before, settled the three.

Fetching a package

The first packages are the core packages, published together as one package called core: strings searches and splits text, strconv turns text into numbers and back, and encoding/json reads and writes JSON, a common format for data. The program in examples/packages/ uses all three:

Check it before it has fetched anything, and every line that names a package says what is missing: 

$ heroes check --brief main.hero
main.hero:9:5: error[unknown_entry]: `<core>` names no entry: there is no catalogue `heroes.toml` beside `main.hero`, the file you compile, and a package's module is read only through its entry there — `heroes add core` writes one
main.hero:10:5: error[unknown_entry]: `<core>` names no entry: there is no catalogue `heroes.toml` beside `main.hero`, the file you compile, and a package's module is read only through its entry there — `heroes add core` writes one
main.hero:11:5: error[unknown_entry]: `<core>` names no entry: there is no catalogue `heroes.toml` beside `main.hero`, the file you compile, and a package's module is read only through its entry there — `heroes add core` writes one

The command that fetches is heroes add, run in the program’s folder. A package is read from an index, a place that lists every version of every package it holds. Today the one index is the folder packages/ at the root of this project’s repository, the folder that holds all its files and their history, so the command names it: 

$ heroes add core --index file://../../packages
added core 0.2.1
wrote heroes.toml

And the program builds and runs: 

$ heroes run main.hero
the-core-packages
value
one
two
-17
{"core":["strings","strconv","encoding/json"],"since":0.1}

heroes add did two things. It wrote a file beside main.hero, the catalogue, and it placed a copy of the package’s files inside the program’s folder. From then on the program needs neither the index nor the network: heroes build, heroes check and heroes run never fetch anything. Only heroes add and heroes fetch reach out, and a package that is missing, or does not match, is an error that names heroes fetch. The sitting that designed the package manager made that a rule: the compiler may use the network only where the answer was written down in advance, and for a package that answer is its fingerprint, further down. Go, the language whose package system this one copies, was measured fetching during a build; a Heroes build never does.

A program that uses no package has no catalogue. Every program in the chapters before this one builds as it always did, with no file beside it: the design was measured from the start on the files a program must have, and the answer for a program that depends on nothing is none.

The catalogue, line by line

index is the address the two commands read packages from. [dependencies.core] opens the entry, and core is the name the code writes between angle brackets. version is exact: no range, no “this one or newer”. sum is the package’s fingerprint, a number computed from every byte of its files, and the build refuses a copy whose bytes give another.

Nobody types the catalogue: heroes add writes it. The sum is sixty-four digits and letters after its sha256-, which nobody can write from memory, so an entry written by hand, by a person or by a model, has no sum to put in it, and the sitting had the specification name the command for that reason.

The format is TOML, a small format for files of settings that Rust’s Cargo and Python’s pyproject.toml use too, read here as a strict subset. Every value is a string between double quotes, so version = 0.2.1 written bare is refused at its line and never read as a number. The file is read whole or not at all: a mistake on any line names no package, the lines above it included. And reading it runs no code. The sitting is plain about what it did not show: in its test with language models every format did equally well, because the models copied the example they were given. TOML was chosen for its comments, its named keys, its strictness and its being familiar from Cargo, and not because models write it better.

Mine and fetched: the angle brackets

Two kinds of use stand side by side in this file. use book/entry is a module of the program, read from its root as in chapter 12. use <core>/strings is the module strings of the package the catalogue calls core. The brackets are the whole difference between mine and fetched, and you see it on the line without opening another file. That was the author’s call, made before the panel sat; the sitting tested it rather than ruled on it, and the two other spellings it tried beside it did no better.

Between the brackets goes a name, never an address. In Go an import carries the address of the repository it comes from; here the address lives in the catalogue, and the code says only core. When a package moves, from a git repository to an index for instance (git is the tool most projects keep their history in), the catalogue’s entry changes and no line of code does. Write an address anyway and the compiler says where it belongs: 

$ heroes check main.hero
error[use_holds_an_address]: `git.example.org/ana/core` is an address, which the catalogue `heroes.toml` beside the file you compile holds and a `use` never does: the `use` names its entry between `<` `>`, then a module of the package — `use <core>/strings`, `core` standing for the entry the catalogue gives that address
  at main.hero:11:5
     |
  11 | use <git.example.org/ana/core>/strings
     |     ^^^^^^^^^^^^^^^^^^^^^^^^^^
  fix (guess): write `<core>`

The two kinds never stand in for each other. A use with brackets is read only through the catalogue, and one without only from the program’s own folders, with no fallback either way. So deleting the catalogue, deleting an entry or mistyping one of its fields never changes which module compiles, only whether the program builds. The design document admits the catalogue on that condition and no other, with one exception, a path entry, which this chapter comes back to.

heroes fmt keeps the two kinds apart on the page as well: packages first, then the program’s own modules, a blank line between, each group sorted by its path. The compiler walks the modules in that same order, so the order you write them in changes nothing it does, only the line numbers of the file.

Where the copy lives

$ ls heroes.packages
core@0.2.1-e8db5b383e666067

heroes add placed the package in a folder of the program called heroes.packages/, under a name made of the entry, its version and sixteen hexadecimal digits (the digits 0 to 9 and the letters a to f) computed from the entry’s fields and the index line. A mistyped field therefore names a folder that is not there, and the build says so. Inside is a byte-for-byte copy of the package’s files as the index publishes them. The program keeps that folder in its repository beside its own files: every program in examples/ that uses core carries its copy there.

No use can spell the folder, because a part of a use path cannot hold a dot. Try, and the compiler answers that this is the folder a fetch placed a package in, “which a use never names”, and offers use <core>/strings. So the copy is reached only through its entry, and with the entry gone the copy compiles nothing: every use <core>/… is refused, the folder still there.

Why inside the program, and not in a cache, a folder every program on the machine shares, as Go keeps one? The sitting’s compiler engineer gave the reasons. Every name the compiler prints of a fetched module is relative to the program and the same on every machine, in its messages and in the line markers of the C it writes, where a debugger, the tool that stops a running program to look inside it, finds the file names. No user’s cache folder is read, so no rule about where each system keeps one enters the compiler. And two programs never share a copy, so two builds never wait for each other. What it costs is a copy per program, and a folder that anything can edit: an editor, a script, a slip of the hand. The second cost is what the fingerprint, checked at every build, is for.

Inside a package, a use starts at its own root

This is the top of core’s strings.hero. Its use strings/internal/scan does not start at your program’s root, where there is no strings/ folder: inside a package, a use starts at the package’s own root, and a use with brackets names an entry of the package’s own catalogue.

The reason is the folder’s name above. The package’s author cannot know it: it holds digits computed from the entry, so it changes with the version and with the index line. The same core 0.2.1, added to a program that reads the index by another path, landed in core@0.2.1-861e1a4ddf9ad992. A use written from the program’s root would have to name that folder; written from the package’s own root it is the same in every program, so a package moves from one program, index or version to the next without one of its use lines changing.

Private modules: internal/

The module strings/internal/scan does the byte-by-byte work of strings, and its first lines say why it stands apart: “kept out of its face because no program calls it”. A module under a folder called internal belongs to the module before the last internal in its path, here strings, and only that module and the modules under it may name it. From a program: 

$ heroes check main.hero
error[private_module]: `<core>/strings/internal/scan` is private to `<core>/strings`: a module under an `internal` folder is named only by the module that folder belongs to and by the modules under it; name what `<core>/strings` offers instead
  at main.hero:11:5
     |
  11 | use <core>/strings/internal/scan
     |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The rule is Go’s, which has had it since Go 1.4, and here it binds your own folders too: in a program with geom/shapes.hero and geom/internal/sq.hero, geom/shapes may write use geom/internal/sq and main.hero may not.

What it buys is a package whose face, the module a program names, is the whole of what a program can depend on. Each package’s card, the short reference beside its face (strings.md beside strings.hero), is written from the face alone. The modules under internal/ are free to change between versions, since no program can have named them, and core 0.2.1 did exactly that: every file it changed or added is under encoding/json/internal/, and the face, encoding/json.hero, is the same file as in 0.2.0.

The fingerprint

Each version an index publishes has a list: one line per file, the file’s SHA-256 and its name, sorted by name. SHA-256 is a standard recipe that turns any bytes into sixty-four hexadecimal digits, and into entirely different ones if a single byte changes. Six lines of core 0.2.1’s list:

The SHA-256 of the list is the version’s fingerprint. The index keeps one line per version in a file called versions, and the catalogue’s sum repeats the line of the version it holds:

Anybody can check those digits with nothing of Heroes, from the root of the repository: 

$ shasum -a 256 packages/core/0.2.1/list
6cf4554fb84b9ecfb0e22a2d8e715e7e1dc20221936aade3dee19d2991b7022c  packages/core/0.2.1/list

The compiler checks the copy in heroes.packages/ against the sum at every build, every check and every run. Change one byte of it, here a 0 made a 1 in strings.hero, and the build stops before it compiles anything: 

$ heroes build main.hero
error[package_unread]: `<core>` cannot be read: the tree placed at `heroes.packages/core@0.2.1-e8db5b383e666067/` is `sha256-7ed4e76f014865c819a1814a5741f3dc06eb41ee949fe807a2c0abd2579aacc4`, and the catalogue's `sum` for it is `sha256-6cf4554fb84b9ecfb0e22a2d8e715e7e1dc20221936aade3dee19d2991b7022c`: a file of it was changed, added or taken out since it was placed — move it out of `heroes.packages/` to keep the change, or remove it, and `heroes fetch` places it again
  at main.hero:9:5
    |
  9 | use <core>/encoding/json
    |     ^^^^^^^^^^^^^^^^^^^^

heroes fetch never writes over the change, because an edit may be the author’s own work: it stops, names the file that changed and says what to do, which is to move the folder out of heroes.packages/ to keep the change, or to remove it to have the published tree placed again: 

$ heroes fetch
heroes.toml:5: error[sum_mismatch]: `core` 0.2.1 from the index `file://../../packages` is placed at `heroes.packages/core@0.2.1-e8db5b383e666067`, and that tree was changed since it was placed: `strings.hero` changed; the change is yours, so nothing was placed over it: move the folder out of `heroes.packages/` to keep the change, or remove it to have the tree placed again

Removed, the tree comes back from the index, which is held to the same standard on the way: each file heroes fetch copies must match its line of the list and the list must match the catalogue’s sum, or nothing is placed. 

$ rm -r heroes.packages/core@0.2.1-e8db5b383e666067
$ heroes fetch
placed core 0.2.1 heroes.packages/core@0.2.1-e8db5b383e666067

Why at every build, and not only when fetching: the copy lives in a folder anything can edit, and an edited copy compiled without a word is the silent failure this language exists to refuse. The check is the SHA-256 of the runtime, the piece of program that sits underneath every Heroes program, written in C, and never a package’s code: in the words of a later sitting, the verifier stays out of the verified, so no package can vouch for itself. Every file counts, .hero or not, because a C header a package carries, the file that tells the compiler how a C library is shaped, is code the program trusts too.

A published version never changes

A version, once published, is never edited: a change to a package is a new version. crates.io, Rust’s index, says it of every crate it holds: “The version can never be overwritten, and the code cannot be deleted.” Here the versions file above has only ever gained lines.

core 0.2.0 to 0.2.1 is the case so far. In 0.2.0, json.parse read a number far from one slowly, by a route whose cost grew with the distance; 0.2.1 reads most numbers with a single multiplication by a 128-bit power of ten, the method Go’s own strconv uses. That change went out as 0.2.1, and 0.2.0 stayed byte for byte as it was published. A program that holds 0.2.0 builds exactly as it did, and one that wants the new version asks for it: 

$ heroes add core@0.2.0 --index file://../../packages
added core 0.2.0
wrote heroes.toml
$ heroes add core
changed core 0.2.0 -> 0.2.1
wrote heroes.toml

A program keeps the version it fetched, so a change to a package never breaks a program’s build: it reaches a program only when the program asks for it.

One version of each package

A program holds one version of each package, and its catalogue lists every package the build compiles, the packages its packages need included. When two of them need two versions of a third, heroes add keeps the higher one: that is Go’s rule, called minimal version selection. Here a small index made for the purpose holds a, which needs strs 1.0.0, and b, which needs strs 1.1.0: 

$ heroes add a --index file://../index3
added a 1.0.0
added strs 1.0.0 for a
wrote heroes.toml
$ heroes add b
added b 1.0.0
changed strs 1.0.0 -> 1.1.0 for b
wrote heroes.toml
$ heroes run main.hero
a sees 1.1.0
b sees 1.1.0

The choice is made once, by the command, and written down; the compiler solves nothing, and a catalogue that leaves out one of those packages is refused, never completed. Since the catalogue holds the whole list with every sum, nothing else stands beside it: no lock file, the second file other systems keep to pin what was chosen. Russ Cox, who designed Go’s rule, wrote that it “leads to reproducible builds without lock files”.

Why one version: a package compiled twice is two packages. Its records become two types with one name, and a value one copy hands out is refused where the other’s is expected. Reach one folder both as a package and as a module of your own, which only a path entry allows, and that is what happens: 

$ heroes check main.hero
note: the package `lib` is read from the folder `lib/`, a `path` entry of the catalogue: unverified, no fingerprint holds it
error[type_mismatch]: expected `counter.Box`, found `own.Box`
  at main.hero:7:22
    |
  7 |     b: counter.Box = own.boxed(3)
    |                      ^^^^^^^^^^^^

Dart records the same failure: one file reached by two spellings, which Dart’s own guide says it takes for “two completely unrelated libraries”.

Two other sources: git, and a folder of your own

An entry can name a git repository instead of an index. A commit is one saved state of a repository, and a tag a name given to one commit, such as v0.1.0. heroes add with an address and --tag writes the address, the tag, the commit the tag names and the sum. The repository here is a local one made for the purpose: 

$ heroes add file://../greet --tag v0.1.0
added greet v0.1.0
wrote heroes.toml
$ cat heroes.toml
[dependencies.greet]
git = "file://../greet"
tag = "v0.1.0"
commit = "e191abf1ce560fd3020d201ed56e76d43dcb1eb6"
sum = "sha256-09cac94c6a5803de196d94dc80c9da89329c20ce2ee673a876de3a4d5ac381d3"

The commit is there because a tag can be moved to another commit. A moved tag is refused, never followed: 

$ heroes fetch
heroes.toml:3: error[tag_moved]: the tag `v0.1.0` of `file://../greet` names the commit 07290184ea57bf707fa8c8e2b30e3a278ebc80fa, and the entry `greet` was written when it named e191abf1ce560fd3020d201ed56e76d43dcb1eb6: a tag that moved is refused, never followed, and `heroes add` writes the entry again once the new commit is the one meant

On the network an address is https://: a plain http:// is refused, being “read in clear, so anything between could change what is fetched”. And file:// is accepted only for a folder inside the program’s own repository, which is how the programs in examples/ read packages/.

The third source is a folder of your own, heroes add --path, for a package you are still writing. It is read where it stands and never copied, and nothing holds it to a fingerprint, so every build says so: 

$ heroes add --path ../../packages/core/0.2.1/files --as core
added core ../../packages/core/0.2.1/files
wrote heroes.toml
$ heroes check main.hero
note: the package `core` is read from the folder `../../packages/core/0.2.1/files/`, a `path` entry of the catalogue: unverified, no fingerprint holds it

It is the one exception to the promise that a catalogue’s mistake never changes which module compiles: a path pointing at the wrong folder compiles other code. The author listed a local folder among the sources, so the sitting kept it, and made it loud rather than silent.

What exists today

One package, core, with three modules a program can name: <core>/strings, <core>/strconv and <core>/encoding/json, each with its card, all written in Heroes, none over a C library. One index, the folder packages/ at the root of the repository, which the programs in examples/ read over file://.

A catalogue with no index line reads the Heroes index, a site that is not built yet: building it, publishing a package to it and deciding who may take a name make a milestone of its own, M-package-index, on the roadmap. Until it exists, a package from outside this repository comes from git, or from a folder of your own. The rules every core package follows, for whoever writes the next one, are the package writer’s guide, beside the program this chapter used.

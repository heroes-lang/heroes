Generics and function values

One function can work with different types and take other functions as arguments.

A generic function can perform the same operation on different types. For example, you can write one function to transform list elements, whether they are numbers or strings. The arguments at each call determine the concrete types.

Declaring type parameters

<A, B> declares two type parameters. The compiler determines the concrete types from the call arguments. In the body, [A] means a list of A values, and out: [B] @ [] declares an empty list of B values. An empty list needs an explicit type because it has no elements to infer it from.

Three rules for generic functions

  • Only functions can be generic. Fields in a record or variant have concrete types. Built-in lists and maps can hold elements of different types.
  • No conditions on the types. There is no way to say “any A, as long as it can be compared”. If a function needs an operation on A, you pass that operation in as an argument, like f above.
  • Do not write type arguments in a call. The compiler infers them from the arguments. If it cannot, it reports an error. The syntax each<i64, str>(…) is not allowed.

Call each with its ordinary arguments; their types give the compiler the information it needs.

Functions are values, and they have names

The name of a function declared at the file’s top level, written without parentheses, is a value you can pass to another function. Heroes has no lambdas, or anonymous functions, and no functions that capture surrounding variables. Every function therefore has a name and a declaration you can read, test and reuse.

Write a function type as (function(A) -> B). The outer parentheses are required: without them, f: function(A) -> B -> [B] would be ambiguous. The compiler reports the error: 

$ heroes check generics.hero
error[expected_type]: expected a type, found `function` — a type is `i64`, `f64`, `bool`, `str`, `[T]`, `{K: V}`, `T?`, `()`, or the name of a `record` or `variant`
  at generics.hero:18:38
     |
  18 | function keep_if<A>(xs: [A], ok_for: function(A) -> bool) -> [A]
     |                                      ^^^^^^^^

Filtering and combining elements

This function has one type parameter because filtering preserves the element type. If you pass a function with incompatible types, the error identifies the argument and shows both types: 

$ heroes check generics.hero
error[type_mismatch]: expected `bool`, found `i64`
  at generics.hero:52:36
     |
  52 |     assert keep_if([-1, 2, -3, 4], double) == [2, 4]
     |                                    ^^^^^^

combine iterates over a list of A values and calculates a result of type B. By changing the step function, you can sum numbers, join strings or count elements that meet a condition.

One generic, three element types

If you pass each a function that returns str, the result is a [str] list. The compiler infers and checks the types in both calls.

The compiler generates a version of each for each combination of concrete types used by the program. The C output therefore contains separate versions for integers and strings. The program does not need to select types at run time or wrap values in a generic container. Additional versions do increase the executable’s size. 

$ heroes run examples/gallery/06-generics.hero
10

The functions map, filter, fold, find, any and all are already available and are written in Heroes. This chapter’s three functions illustrate how they work under different names, because you cannot redefine a built-in name.

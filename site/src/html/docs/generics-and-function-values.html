Generics and function values

One shape for many types, and no anonymous functions anywhere.

Writing the same loop once for lists of numbers, once for lists of words and once for everything else is the best way to throw away an afternoon. Building a type system that can express every imaginable condition on that loop is the best way to throw away the next ten years. Heroes takes the smallest thing that works: a function may leave the type it works on open, and that is the whole feature.

A function with a hole in its types

<A, B> after the name puts two types in play that the function does not know yet: whoever calls it supplies them. Inside they behave like real types, so [A] is a list of the first kind and out: [B] @ [] is a list of the second, still empty. The empty list has to be told its type for the usual reason: there is nothing inside [] to work it out from.

Three rules, and they are all absences

  • Only functions can leave a type open. A record or a variant always has its types settled. When you need a container that works for any type, a list or a map already is one.
  • No conditions on the types. There is no way to say “any A, as long as it can be compared”. If a function needs an operation on A, you pass that operation in as an argument, like f above.
  • Never written when you call. The compiler works the types out from the arguments you give it, or it is an error. each<i64, str>(…) is not a spelling the language has.

The third one is the surprising one and it follows from the second: with no constraints there is nothing to disambiguate, so a type argument would only ever repeat what the compiler already knows.

Functions are values, and they have names

A top-level function used without brackets is a value you can pass. There are no lambdas: nothing anonymous, nothing that captures the variables around it. So the thing being passed always has a name, a signature and, usually, a comment, and it can be read, tested and reused on its own. What you give up is the one-liner written inline at the call site; what you get back is that every piece of behaviour in the program is somewhere you can point at.

A function type is written (function(A) -> B), and those outer brackets are not decoration. Without them, f: function(A) -> B -> [B] could be read two ways, and the compiler says so rather than picking one: 

$ heroes check generics.hero
error[expected_type]: expected a type, found `function` — a type is `i64`, `f64`, `bool`, `str`, `[T]`, `{K: V}`, `T?`, `()`, or the name of a `record` or `variant`
  at generics.hero:18:38
     |
  18 | function keep_if<A>(xs: [A], ok_for: function(A) -> bool) -> [A]
     |                                      ^^^^^^^^

Filtering, and putting things together

One type parameter here, because filtering does not change the element type. Hand it a function of the wrong shape and the error lands on the argument, naming both types: 

$ heroes check generics.hero
error[type_mismatch]: expected `bool`, found `i64`
  at generics.hero:52:36
     |
  52 |     assert keep_if([-1, 2, -3, 4], double) == [2, 4]
     |                                    ^^^^^^

combine is the general one: it walks a list of A and builds up a B, so summing numbers, joining strings and counting matches are all the same function with a different step.

One generic, three element types

The second line is the whole point: the same each, given a function that returns str, returns a [str]. Nothing at either call site says so, and both are checked completely. 

$ heroes run examples/gallery/06-generics.hero
10

map, filter, fold, find, any and all already exist with these shapes, and they are written in Heroes rather than built into the compiler. The three functions above are those shapes under different names, because no file may redeclare a built-in one.

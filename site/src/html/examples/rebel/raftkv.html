Raft, the method by which several machines agree on one history of data, and a key-value store copied onto each, put to the test in a simulated network.

Each machine of the group, a node, keeps a record, the log, of the operations of the clients, the programs that use the store: the value of a key written, the key being the name it is found by, a key deleted, a text added at its end. A node becomes leader by the vote of the majority, after a wait drawn at random from a generator with a seed, the number from which a random sequence always comes out the same; the leader copies every operation onto the others and counts it final, committed, once the majority holds it. Each node saves its state in files of its own, every record with a checksum, a number computed from the contents that changes if the file is damaged, and after a crash it starts again from those alone, even when it stopped in the middle of a write. The log is cut short by a snapshot, a picture of the store that takes the place of the old entries, and a node left behind receives it in parts. A read is linearizable: the leader answers only after the majority has confirmed that it still leads, so nobody reads a value already replaced. Nodes are added and removed one at a time. A checker asks, after every step, Raft’s safety properties, the ones that must hold whatever fails.

The output on this page is its demo, run on the scenarios of its folder, written in TOML, a format for configuration files: a leader elected, writes and a read; a partition, the network cut in two, that leaves the old leader without a majority, so it confirms no write and answers no read, while the others elect a second leader; the network healed and the old leader’s entries removed; a node stopped in the middle of a write that, started again, catches up from the leader’s snapshot; a node that joins and one that leaves. Then a node left alone loses its election because its log is behind, and the same steps with a bug planted on purpose, votes given without looking at the log, which the checker finds. Last, a node’s disk read back and a few runs of the fuzzer, which draws the failures from a seed. The simulated network is a scheduler, a program that decides the time of every delivery, so the same seed gives the same run, byte for byte, on every machine. Rebel’s random draws the waits and the failures, containers/heap orders the messages in flight, bytes and hash write the format of the messages and the files, fs and path keep each node’s folder, json writes the snapshot, toml and time read the scenarios, and flags the command line.

The build log

· changes ·

One entry for each stage of the project, newest first. Full reports, including decisions, reviews and problems encountered, are in the repository. They will be available when the code becomes public.

  1. Freeing strings returned by C An extern declaration can name the function that frees a string allocated by a C library. The compiler calls it automatically. The change also exposed an incorrect count of the functions used in the SQLite example. The SQLite example
  2. Checking thread stack space Threads started by Heroes now report when they run out of space for function calls. A reviewer verified that a thread created by a C library is stopped by an earlier check that names the Heroes function involved. How to use threads
  3. Separate memory for each thread Each Heroes thread, an operation running in parallel, manages separate memory. The review found a missing check in callbacks, functions called back by C: it allowed a list to cross the C interface without being reported. Thread examples
  4. Passing Heroes functions to C libraries You can pass a Heroes function to atexit or pthread_create. The callbacks required by qsort and signal are not supported yet. The compiler reports the limit at the declaration. A reviewer examined the full SQLite header and found different obstacles from those suggested by the initial examples. The C boundary
  5. Larger examples to test the compiler More complex programs were added to cover the gap between small examples and the compiler. Two reviewers rejected the proposed optimisation. One then identified excessive memory use by temporary values that the proposal had not considered. The programs
  6. An error when passing array elements A comment described a crash as impossible, but one line could reproduce it. Passing an array element to a function that modifies it gave C the address of the whole array. The examples covered record fields but missed this case. What the compiler stops
  7. Documenting modules The documentation lacked an explanation of how to organise a program’s files. A chapter on modules was added. Read the chapter
  8. Expanding the examples New programs were chosen to test more parts of the language. The first found a defect: it passed type checking, but compilation failed with an internal error. The chapters
  9. Organising source files into directories The compiler’s files were organised into directories. Directory structure replaced long filename prefixes, allowing shorter names. The compiler in its own language
  10. Using paths for modules Modules can be found in subdirectories using a path. Previously, all files had to be in the same directory. The panel examined the new rules over several reviews. Modules and files
  11. Running commands without a shell The compiler started tools by building a string for the shell, the program that interprets commands. On Windows, the same options were interpreted differently and created a directory with the wrong name. The problem led to passing arguments directly to the process. Why the language is shaped this way
  12. Compiling one module at a time Compilation generated one large C file even after a small change. Code generation was split by module so results for unchanged parts could be reused. One C file per module
  13. Archiving the first compiler The first compiler was archived. The work revealed that it also contained several tools used to measure and check the project. The current compiler
  14. Writing the test tools in Heroes The tools that check the compiler were rewritten in Heroes. They run commands, read the results and compare them with expected output, testing the compiler as a person would use it.
  15. Distributing the compiler as a C file Building the compiler requires compiling one generated C file with clang. The repository includes this file, so a computer without Heroes can build the compiler.
  16. The compiler written in Heroes The compiler was converted from Rust to Heroes, together with its tests. Compiling its own source exposed defects in both the new version and its predecessor. Examples and tests with expected results checked the conversion. How to verify the compiler
  17. Converting the first module The first trial converted one file and recorded any limits encountered. The expected limit had already been removed by another change. The lexer, which divides source text into recognisable elements, worked without the predicted obstacle.
  18. Completing support for C structures More C declarations became usable from Heroes. The work corrected compiler rejections that prevented forms already allowed by the language.
  19. Passing structures to C functions C structures group several fields into one value, but Heroes could not yet pass them to functions. This limitation blocked many operations in a real library.
  20. Checking C function parameters The compiler checked C function results but not their parameters. Declaration checks were extended to input types.
  21. Finding defects with complete programs The first complete programs found new compiler defects. They included a JSON reader, Markdown converter, spreadsheet, maze solver, assembler, log analyser and game.
  22. Integers of different widths Heroes introduced eight integer types with explicit widths. The word int is rejected because it does not specify a type. This required revisiting an initial design restriction.
  23. Making numeric bases explicit A reviewer wrote 0700 for file permissions and asked how it was interpreted. The question exposed the need for clear rules to distinguish numeric bases.
  24. Using constants from C headers C library options can be named in the program. Previously, programs had to copy their numeric values by hand. Reading the value from the header removes that duplication.
  25. Checking declarations against headers An example returned 1 where 1.41 was expected: C declaration checking had a defect. Verification must compare the Heroes declaration with the actual header through clang.
  26. Defining module names Programs can be split into files. Rules were defined for name conflicts and imported modules that are not used.
  27. Completing generics and core operations Generic functions and core operations were completed. Open questions were checked with the compiler, including how types are represented during execution.
  28. Maps and fallible results Implementing maps depended on values that represent a result or an error. Looking up a key can return its associated value or an error if the key is missing.
  29. Representing recursive data Heroes can represent an expression tree without mutable references between values. Each node holds its children through an array.
  30. Managing string memory The compiler introduced reference counting to free memory. Checks challenged the initial rule, which released each string at the end of the block that created it.
  31. Producing the first executable A Heroes program was compiled into a native executable. The work also raised the question of which exit status to use when a program is valid but the compiler does not yet support everything it needs.
  32. Choosing the internal representation The compiler’s intermediate representation of a program was defined. LLVM guidance led to starting with memory locations, reads and writes, leaving optimisation to a later pass.
  33. Measuring the first checks Name, type and missing-case checks were tested by introducing mistakes into working programs. Comparing them with the Heroes-specific checks disabled measured the effect of those rules.
  34. Connecting names to declarations Name checking rejected two declarations in a calculator program. The program defined map and fold, but both names were already reserved by the language.
  35. Parsing and formatting code Writing the parser, which recognises code structure, revealed a contradiction in the specification. fn was both a forbidden word and the prescribed form for a function type. Parameters of that type could not be declared.
  36. Splitting source into tokens The first compiler component divides source text into tokens, the elements the compiler recognises. Implementation exposed problems that the design alone had not revealed.
  37. Preparing the project and tests The Rust project, test tools and first example programs were prepared. The specification became the reference. Its initial size limit was still an estimate and changed when tokens were counted.
  38. Reviewing the plan Five reviewers critically examined the plan before implementation. They assessed language design, compiler engineering, simplicity, use by models and teaching.
  39. The initial idea The project began with a document and a discussion about the language. The aim was a compiled language that used C libraries and was designed for models that generate code.

Full reviews, measurements and journals are in the repository, which will open with the code. Follow the feed for updates, including the announcement when the repository becomes public.

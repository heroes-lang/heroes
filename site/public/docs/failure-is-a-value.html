Failure is a value

There is no null, and there are no exceptions.

Most languages give you two ways for something to be missing or to go wrong, and both of them are invisible in the code that uses them. A value might be null, and nothing on the line tells you whether it is. A call might throw, and nothing on the line tells you whether it does. Both produce the same class of bug: the unhandled path — the one kind of mistake that raises no compile error, in any language that has it.

That is the class Heroes exists to remove, so it has neither. Instead, a function that can fail says so in its type, and every reader — human or model — can see it without opening another file.

A type that means "or an error"

Write i64? and you have said: this is a whole number, or an error explaining why there isn't one. There is no third possibility, and there is no way to use the number without dealing with the other case. Inside such a function, ok(v) makes the good answer and fail(code, msg) makes the bad one:

The error carries two things, and both are deliberate. The code — "not_a_digit" — is a short, stable name in snake_case, meant to be compared by a program: it is the part that does not change when somebody improves the wording. The message is for whoever reads the failure. Codes are how you branch on what went wrong; messages are how you explain it.

Handing a failure upwards: ?

Most of the time a function that hits a failure has nothing useful to add and simply wants to stop and pass it along. That is what ? does, and it does it visibly, on the line where it happens:

Read the loop body. digit_of(text[i])? means: call it, and if it failed, stop this function now and return that same error to my caller. If it succeeded, carry on with the number it produced. One character of syntax, in the exact place the control flow forks — which is the whole difference from an exception. An exception also jumps out of the function, but it does it from a line that looks like it cannot.

Two other things are visible in that function, and both are worth naming now. total: i64 @ 0 declares something that will change: the @ marks mutability, and a name without it can never be reassigned. And text.len() is the same call as len(text) — method syntax is sugar, so a chain reads left to right without anything being defined on a type.

Notice also what isn't there: no try, no catch, no nesting, no error variable threaded through by hand. The failure path costs one character and the happy path reads as if failure were impossible. Looking inside: match

When a function does want to handle the failure rather than pass it on, it looks with match — the one construct in the language for taking a value apart:

Both arms are required. A match that forgets a case does not compile, and — this is the part that matters for the thesis — a catch-all arm is forbidden here. You cannot write the arm that means "anything else", because that arm is how a forgotten case silently becomes a handled one. If the language ever gains a third possibility, every match in every program stops compiling until somebody has looked at it. That is the intent: a change to the shape of the data should break the code that reads it, loudly, at build time.

When you genuinely don't care

Sometimes a failure really does have an obvious answer, and writing a match for it is noise. Two shorthands exist:

.default(0) says: the value, or this if it failed. The result is a plain i64 — the failure has been dealt with, so the type no longer carries one. Its sibling is .must(), which says the failure cannot happen here and stops the program if it does. Use it where you have already proved the value is good, and in tests:

What this buys

Every function's signature tells you whether it can fail. Every place a failure changes the control flow is marked on that line. Every way of handling one either deals with both cases or says out loud that it is skipping the check. There is no null to forget and no throw to miss, and the unhandled path — the one bug that no compiler catches in the languages that allow it — has nowhere left to hide.

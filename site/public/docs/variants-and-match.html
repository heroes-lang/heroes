Variants and match

A value that is one of several shapes, and the one construct that opens it.

A record says and: a point has an x and a y. A variant says or: a token is a number or a word or a plus sign. Some of its cases carry data and some are just themselves, and a value of that type is exactly one of them at a time.

Declaring one

Six cases. number and word carry a payload, written as fields indented under the case name, exactly the way a record writes its own. The other four carry nothing: plus is a complete value on its own.

Opening one: match

match is the only construct in the language that takes a value apart. There is no way to ask which case is this and then reach inside; the question and the answer are one thing:

An arm names its case with a leading dot, then =>, then the answer. A case that carries a payload binds it to a name after the dotted name: .number n would give you n, and n.value is the number inside. Here nothing needs the payload, so it is _, which binds nothing and can be repeated.

match is an expression: it has a value, which is why this whole function is one return. It can also stand alone as a statement when the arms do something rather than produce something.

Every case, or it does not compile

Leave one out and the build stops. This is the file above with its last arm deleted: 

$ heroes check tokens.hero
error[non_exhaustive]: this `match` does not cover `.close`
  at tokens.hero:19:12
     |
  19 |     return match t
     |            ^

And there is no _ to hide behind

In most languages you would answer that error with a catch-all arm. Here that arm does not exist over a variant, and the message says why: 

$ heroes check tokens.hero
error[wildcard_on_variant]: `_` is not allowed as an arm over `Token` — name every case, so that adding one breaks this `match` instead of silently falling through
  at tokens.hero:25:9
     |
  25 |         _         => "something else"
     |         ^

_ is still fine where being exhaustive is impossible (matching on an i64 or a str), because there the alternative is not a check, it is an infinite list.

Why that rule is the whole point

Add a seventh case to Token, say a minus, and ask the compiler what it thinks: 

$ heroes check tokens.hero
error[non_exhaustive]: this `match` does not cover `.minus`
  at tokens.hero:20:12
     |
  20 |     return match t
     |            ^

error[non_exhaustive]: this `match` does not cover `.minus`
  at tokens.hero:30:12
     |
  30 |     return match t
     |            ^

error[non_exhaustive]: this `match` does not cover `.minus`
  at tokens.hero:38:12
     |
  38 |     return match t
     |            ^

Three errors, one per place in the file that reads a token, each pointing at the match that now has a hole in it. Nothing runs until a human or a model, has decided what a minus sign is called, what its binding power is, and whether it is an operator. A change to the shape of the data breaks the code that reads it, loudly, at build time. With a catch-all arm, all three of those questions would have been answered silently and wrongly, and the program would have run.

Two cases, one answer

It is not a catch-all wearing a disguise: every case is still written down, so the new minus would still break this function, which is right, because whether a minus is an operator is a real question.

Making one

$ heroes run examples/gallery/02-tokens.hero
`(`
a number
`+`
a word
`)`

A case with no payload is written .plus; one with a payload is a call whose fields are named, .number(value: 12), the same rule records follow. And the leading dot means the value knows which case it is but not which type it belongs to, so the list needs the annotation : [Token] to say it. Written once, it checks every element.

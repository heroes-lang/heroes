Un primo programma

Un file, un main, e niente intorno.

Quasi tutti i linguaggi chiedono un po’ di cerimoniale prima che la tua prima riga possa girare: l’import della cosa che stampa, una classe che contenga la funzione, un file di progetto che dica quali file esistono. Heroes non chiede niente di tutto questo. Un programma è un file, e un file che può girare è quello che dichiara main.

Il programma, tutto quanto

$ heroes run examples/gallery/00-first.hero
20

function main() dichiara da dove parte il programma. Non prende niente e non restituisce niente: per questo dopo le parentesi non c’è né una freccia né un tipo. Una funzione che restituisce qualcosa lo dice con -> i64, una che non restituisce niente sta zitta. print è dentro il linguaggio, non importato da qualche parte: scrive i suoi argomenti uno dopo l’altro e chiude la riga.

Che cosa non c’è, in quel file

Ognuna delle assenze qui sotto è una scelta, e il motivo è sempre lo stesso: meno posti dove un’informazione può nascondersi, meno modi ci sono di sbagliarsi — per una persona come per un modello.

  • Nessuna riga di import o include. print, len e gli altri nomi predefiniti ci sono e basta.
  • Nessuna classe e nessun blocco namespace. L’unità è già il file.
  • Niente punto e virgola e niente parentesi graffe. Una riga finisce dove finisce la riga, e un blocco è ciò che sta indentato sotto.
  • Nessun file di progetto, nessun manifest, nessuno script di build. Al compilatore dai un file, non una configurazione.
  • Nessuna dichiarazione anticipata. L’ordine delle dichiarazioni non conta mai, quindi due funzioni possono chiamarsi a vicenda senza che nessuna delle due vada annunciata prima.

L’indentazione è la struttura

Un blocco sta quattro spazi più in dentro della riga che lo apre. Non tre, non otto, non un tab: esattamente quattro, a ogni livello. È rigido apposta, e il compilatore te lo dice invece di indovinare cosa volevi: 

$ heroes check hello.hero
error[indentation_not_multiple_of_4]: indentation must be exactly 4 spaces per level; found 2
  at hello.hero:2:1
    |
  2 |   print("hi")
    | ^^

Un tab è un errore a parte, con un messaggio suo. Il senso della regola è che esiste un modo solo di scrivere un programma: due file che fanno la stessa cosa si somigliano, e una differenza in un diff è una differenza di significato. Se ti capita di allontanartene, heroes fmt ti stampa quella forma unica.

La documentazione sta nei commenti

Non c’è una sintassi di documentazione da imparare a parte, perché un commento lo è già. # arriva a fine riga e dentro può contenere markdown; ## apre una sezione, ed è così che un file si prende un titolo e dei capoversi:

Un commento messo subito sopra una dichiarazione documenta quella dichiarazione. Non c’è nient’altro che lo marchi come documentazione, e non serve:

Un file è un modulo

Quando un file solo non basta, il file accanto è un modulo a cui puoi dare un nome. Lo si tira dentro con use:

Quella riga lega eval.hero, nella stessa cartella, al nome eval, e da lì in poi tutto quello che quel file dichiara si scrive con quel nome davanti: eval.calculate(text, env). Non esistono alias e non esiste l’import con l’asterisco, quindi un nome qualificato dice sempre da dove arriva, e ogni modulo che usi vuole la sua riga use. Cercare un nome che non conosci è una lettura, mai una ricerca.

I verbi

Fa tutto un binario solo, e ogni sottocomando risponde a una domanda diversa sullo stesso file: 

$ heroes check program.hero    # nomi e tipi, senza produrre un binario
$ heroes run program.hero      # compila ed esegue
$ heroes build program.hero    # compila e basta
$ heroes test program.hero     # esegue i test del file
$ heroes fmt program.hero      # stampa la forma canonica

Quello interessante è test, perché i test fanno parte del linguaggio e non sono una libreria che scegli tu. Il file dei punti qui sopra ne porta due: 

$ heroes test examples/gallery/01-points.hero
ok   "the 3-4-5 triangle"
ok   "a rectangle keeps its size when it moves"
2 tests, all passed
